Taking Turns

● Advanced4 minBefore this: TasksSpec 9.7

Tasks take turns in an order the language defines, so a program with tasks prints the same thing on every run.

In simple terms

Tasks take turns by fixed rules, like players in a board game. Because the order never changes, the program prints the same thing every time, so a bug you see once you can see again, and fix.

Step through it, with what the machine does between the turns:

main spawns slow. The runtime, while running, makes it a coroutine on main's thread, with its own stack, and puts it in the ready queue. The task that spawned it keeps running.
Native code, one thread. With no task ever spawned, time.sleep_ms is a plain thread sleep: there is no scheduler then. The interpreter (kavach run) gives each task an OS thread instead, with the same turns. The OS picks the core.
Every step, as text
  1. Line 10: const slow = spawn report("slow", 400)
    main spawns slow. The runtime, while running, makes it a coroutine on main's thread, with its own stack, and puts it in the ready queue. The task that spawned it keeps running.
  2. Line 11: const fast = spawn report("fast", 100)
    fast too, behind slow in the ready queue. Both are ready, but main still has the turn.
  3. Line 12: print("both started")
    So main prints first.
  4. Line 13: print(`{try slow.wait()} and {try fast.wait()} are back`)
    main waits for slow and gives up its turn. The scheduler, while running, runs the task that became ready first: slow. The switch is a change of stacks on the same thread, with no system call.
  5. Line 4: time.sleep_ms(ms)
    slow asks to sleep 400 ms. The scheduler notes a timer, counted from when slow became ready, and parks slow: no thread sleeps for it, and no core is held. fast runs.
  6. Line 4: time.sleep_ms(ms)
    fast parks too, with a timer at 100 ms. Now nothing is ready. The scheduler, while running, takes the earliest timer, 100 ms, and the thread waits on a condition variable until then: the OS takes it off the core, which is free for other programs. (A task waiting on a socket would make it wait on the OS's readiness queue instead: epoll, kqueue or IOCP.)
  7. Line 5: print(`{name} done`)
    At 100 ms the OS wakes the thread. The scheduler finds fast's time has come and makes it ready, and it is the only one: fast prints.
  8. Line 6: name
    fast returns its name and ends; its stack is freed. Nothing is ready, so the thread waits again, now until 400 ms.
  9. Line 5: print(`{name} done`)
    At 400 ms slow wakes and prints. The sleeps overlapped: slow's 400 ms began at the same moment as fast's 100.
  10. Line 13: print(`{try slow.wait()} and {try fast.wait()} are back`)
    slow ended, which main waited for, so main runs. fast ended long ago, so fast.wait() doesn't wait. About 400 ms in all, not 500, and the same order on every run: the scheduler decides it from the program, not from the machine.

  • spawn makes the new task ready; the task that spawned it keeps running.
  • A task runs until it waits. Then the task that became ready first runs.
  • When no task is ready, the program waits for the earliest of them.
  • A sleep counts from when its task became ready, not from when the machine got round to running it. A task that waited for its turn has that wait taken off its next sleep, so a busy machine can't change the order.
A machine that stalls can't be written in Kavach, so this rule is tested in the runtime's own Rust tests, where a turn can be made to start late:
a late turn, tested
Why it matters: a bug in a program with threads often shows up once in a hundred runs. With fixed turns, the same program does the same thing every time, so a bug that happens once happens every time, and can be found.
