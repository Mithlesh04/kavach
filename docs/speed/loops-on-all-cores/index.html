Loops on All Cores

Also known as: parallel multithreading threads concurrency simd auto parallelization openmp rayon performance cores

● Advanced6 minBefore this: For Loop, How Kavach Is Fast

Every loop runs on one core, in order, unless you write on cores before it. Then its rounds run on all the program's cores, and the compiler checks that the answer is the one-core answer, exactly.

In simple terms

Like splitting a pile of exam papers among several teachers: each marks a part, and the totals are added at the end. You ask for it with on cores, and Kavach agrees only when the answer comes out exactly the same.

for i in 0..16 { out[i] = math.sqrt(xs[i]) }

A loop of 16 rounds, each writing out[i] from xs[i]. Written plainly, one core would run round 0, then 1, then 2…

Loops too small to gain still run on one core. A sum of floats is refused, as its result depends on the order of adding.

A plain for runs on one core, in order, as in C, Go, Rust and JavaScript. Write on cores before it, and its rounds are cut into chunks that run on all the program's cores at once. Each round here writes its own item, ys[i]:

In for (i, x) in xs.enumerate(), the index i names the round's own slot in the same way:

A round may also add whole numbers into a let with +=. Each core sums its part, and the parts are added at the end, since whole numbers add up the same in any grouping:

total = total + n is the same as total += n. A sum kept modulo a number written in the code works too, as whole numbers give the same remainder in any grouping:

Native code spreads that one over the cores only where the compiler proves no part is negative; elsewhere it runs in order. The answer is the same either way.

An overflow is still caught at the plain loop's round. The program stops with the same message the loop gives on one core:

What on cores refuses

Only three kinds of change keep the one-core answer: writing the round's own slot (out[i], where i is the loop's name or its enumerate() index), writing its own row of a grid kept in one list (below), and adding whole numbers into a let. Anything else is a compile error that says why. print would show the rounds in a different order on each run:

Adding floats in another order changes their last bits, so a float += is refused, with the fix:

Any other change to something every round shares is refused too. Here the last multiple of 7 depends on which round runs last:

For each of these, keep the plain loop, or collect each round's value in its own slot and finish the work after the loop. What a round reads is never limited.

How many cores

on cores uses all the cores the program may use. on cores(n) asks for at most n; asking for more than the machine has uses all it may, so the same program runs on any machine:

  • The program's cap is all the machine's cores, or fewer: cores = 4 under [run] in kavach.toml, or KAVACH_CORES=4 when it starts, which wins when both are set. KAVACH_CORES=1 keeps every loop on one core.
  • Asking for more cores than the machine has uses all it has. With KAVACH_PAR_LOG set, the program says so when it starts, for example kavach: 11 cores asked for, and this machine has 10: using 10.
  • A container or CPU limit counts: under docker --cpus=2, the cap is 2.
  • system.cores() reports the cap, so a program that sizes its work by it follows the cap too.

Leaving early

return, break, continue, fail and ? work as on one core: the first round in order that leaves decides, and rounds after it change nothing. Here the first item over 998 is at 999, however the rounds were shared out:

Nested loops

on covers the one loop after it. A loop inside it runs on one core in each round, unless it has its own on. A label comes first: rows: on cores for …. Here each round builds one row and writes it to its own slot:

  • while can't take on: each round depends on the one before.
  • on, cores and threads are ordinary names everywhere else.

A grid kept in one list

Images and matrices are often one long list, row after row. A round may write its own row of it, grid[row * w + col] inside for col in 0..w, where row is the loop's name:

  • The parts may come in any order: grid[col + w * row] is the same row.
  • w must be unable to change: a number written in the code, a const or a parameter. With a let, rows could overlap, so it is refused:

A list is written one way in a loop: its own slots, or its rows with one w. Written both ways, two rounds could reach the same item, so that is a compile error too:

A built program spreads the rows over the cores by how many items they hold, so even a few long rows are shared out.

Rounds that wait: on threads

on cores is for rounds that compute. For rounds that mostly wait, on the network, a disk or a timer, write on threads(n). Its rounds run at the same time, at most n at once, and may do I/O and print:

  • The three waits overlap, so the loop takes about as long as the longest, not their sum.
  • What rounds print comes in the order of their turns: the round that waits least prints first.
  • The result is still the one-core result. Each round gets copies of what it reads, and its slot writes and whole-number sums are applied in round order, so sizes is [0, 10, 20] on every run.
  • Each round is a task of its own, as spawn thread makes it. Before round i starts, round i - n is waited for, as parallel_map does, so threads(1) runs one round at a time.
  • A loop whose body can leave early (break, return, fail, ?) runs its rounds one after another, so the first round in order that leaves decides.
  • threads(n) may be more than the cores, as its rounds mostly wait.
  • The whole program runs at most [run] threads rounds at once (256 by default), across all its on threads loops. At the cap, a loop waits for its own oldest round before starting another. A loop with no round running still starts one, so nested loops can't wait for each other forever. With threads = 1, each round ends before the next begins, whatever threads(n) asks.

Before a value

on also goes before a value, to say where the work inside it runs. on cores(n) limits library work, such as a big sort or a matrix @, to at most n cores. on cpu keeps its GPU maps on the CPU:

  • It covers the one value after it, and gives the same value as without it.

What Kavach does for you

  • One word puts a loop on every core

    on cores before a for splits it over all cores, and the compiler checks the result is exactly the one-core result, overflow checks included.

    decision 0126

Go deeper the why, for readers who want it

Each chunk runs quietly: where the plain loop would panic, the chunk returns a flag instead. The runtime then throws the chunks' work away and runs the plain loop on one core, which panics at the exact round and line you would have seen. Whole-number sums also record the highest and lowest each chunk's total reached, so a total that would overflow in the middle, in one-core order, is caught too.
