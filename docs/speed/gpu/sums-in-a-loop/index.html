GPU: Sums in a loop

Also known as: overlap streaming pipeline stall reduce accumulate running total big file chunks kavach check note waits async dma

● Advanced4 minBefore this: GPU: map on the GPU

A loop that adds up what the GPU works out doesn't wait for each sum, so the next chunk is read and copied over while the GPU works.

In simple terms

A baker puts the next tray in the oven while the last one bakes, and writes each tray's count in the book when it comes out, in order. The book ends up the same, and the baking takes less time.

There is nothing to write. In a compiled program, a loop of this shape goes on while the GPU works:

The loop goes on when all of this holds:

  • A statement like total += xs.map(f).sum(g) sets the total, with sum, min or max of a list a GPU map or filter made.
  • That statement is the only place the loop mentions total.
  • It only works out numbers, from values the loop doesn't change.

A const s = xs.map(f).sum(g) used once, in the next statement, counts as part of it.

Only the time changes

  • Each statement still runs once for each round, in order, with its checks, before any code after the loop. So total is right whenever it can be read.
  • A few rounds' work may be under way at once, fewer for big chunks.
  • Only the moment of a panic shows. If a statement overflows, the code after it in the loop, and later rounds, may have run by then, as for a map that doesn't wait.
  • Plain kavach run doesn't use the GPU, so its loops run as written, with the same answers.

Which loops wait

kavach check says which loops still wait for the GPU, and why, with the line to look at. A note isn't an error: it goes to standard error, and the exit code stays 0. kavach check --format json leaves the notes out. These are all the reasons:

What it saves

This loop on a file of 2 GB, on the same machine as CUDA, a C++ program that manages its own overlap. 7 runs in turns against a compiler from before this change, in ms, with the same sum every time and the same as CUDA's:

Read and as_list, no GPU1,392–1,581660–894
A gpu fn of 1 step, then sum3,124–3,7601,371–1,8961,012–1,083
A gpu fn of 200 steps, then sum5,525–8,7433,952–4,9421,148–1,222
  • This table comes from before a cheaper check in the kernel: a multiply no longer divides to check two numbers of 16 bits, which can't overflow. Over 5 runs in turns, the 200 steps then went from 4,008–4,062 to 2,785–2,991 ms, and the 1 step stayed at 1,217–1,297 against 1,235–1,468. Results and panics are the same.
  • The laptop was in use while it measured, so two runs far from the rest are left out, both of the old compiler. CUDA's column is 5 runs, from a comparison in turns the same day.
  • A file of 8 GB, too large for the GPU and the system's cache, took 63–65 s in all four cases, Kavach and CUDA: there the disk sets the speed, and neither loop holds it up.

  • as_list no longer copies a big chunk: the chunk is read straight into the list's memory, and as_list takes it when nothing else holds the chunk.
  • A kernel divides through unsigned numbers. On this GPU a signed % took about a third longer than an unsigned one. Results and panics are the same.
  • CUDA is still about 1.8× ahead on 1 step and 2.6× on 200. Up to about 200 steps the time hardly changes, for either: the kernel runs while the next chunk is read, so the difference is the CPU's work for each chunk.
  • Copying a chunk over to the GPU takes as long as CUDA's copy. But the GPU library made a new 64 MB buffer to copy through every few chunks, so Kavach now copies through two buffers of its own, used in turn. Run 6 times in turns, 32 chunks held in memory went from 869 to 764 ms (the uploads alone 410 → 304), and the 1-step stream from about 1,250 to 1,040 ms. Most of what is left is opening the GPU, which Kavach's time includes and CUDA's doesn't.
  • Past that, the kernel sets the speed. The same kernel written by hand, at 800 steps, took 7.1 s with today's checks, 5.3 s without them, and 4.3 s with wgpu's own counter in each loop off too, against CUDA's 1.7 s. That counter stops a kernel that never ends. So since decision 0077, a kernel whose every loop is a for over a range that stops before its end goes without it: over 5 runs in turns the same day, 200 steps went from 2,816 to 2,541 and 800 steps from 6,007 to 4,909, against CUDA's 1,062 and 2,233 ms, with the same sums. A while or a ..= range keeps the counter.
