GPU: Drawing triangles

● Advanced9 minBefore this: GPU: gpu fn, GPU Screens

A gpu vertex fn places each corner of a triangle, a gpu fragment fn colors each pixel inside it, and gpu.pipeline joins the two for frame.draw, with depth for 3D and textures for pictures.

In simple terms

A picture on a screen is made of many small triangles. For each corner, the GPU asks one function where it goes. For each pixel inside, it asks another what color it is. You write both functions in Kavach, and the GPU runs them for millions of pixels at once.

This is the spec's example: dots of a swarm, each drawn as a square, under a camera. It draws into a window, so it is shown here, not run:

  • A gpu vertex fn takes the vertex, then the instance and the value shared by the whole draw, if the draw has them, in that order. It gives a record whose position is where the corner lands: x and y from -1 to 1 across the window, then depth and w.
  • Its other fields go to the fragment fn, blended between the triangle's corners.
  • A gpu fragment fn gives the pixel's color: red, green, blue and opacity, each from 0 to 1.
  • frame.draw(dots, square, instances: swarm, shared: camera) draws the square once for each dot. A draw paints over what the frame already holds.
  • Each three vertices make a triangle. indices: names them by their place instead, so triangles share corners: see GPU Screens.
  • A vertex, an instance or a shared value is a record of 1 to 8 fields, each a Float32, Int32 or UInt32.
  • A list a GPU map made, still in GPU memory, is drawn from there with nothing copied, as vertices or instances. A swarm moved by a map each frame is drawn where it is, and never comes back to the CPU.

The same fns on the CPU

A vertex or fragment fn is an ordinary function on the CPU too. So you can call it with one corner and see what the GPU would get, in a test or a print, with no window:

Depth: the nearest pixel wins

A pipeline made with depth: true draws a pixel only where it is nearer than what is already there. So a 3D scene can be drawn in any order, and a near box still hides the wall behind it. Shown, not run:

  • A pixel's depth is the third part of position divided by the fourth: 0 is nearest, 1 farthest. Only pixels from 0 to 1 are drawn.
  • Each frame keeps one depth for each pixel. They start at 1, the farthest, and frame.clear sets them back to 1.
  • A pipeline without depth, the default, neither looks at the depths nor changes them: it draws over what is there.

depth: is part of the pipeline, which is compiled before it draws. So it is written true or false, never a value worked out while the program runs:

Textures: drawing pictures

A gpu fragment fn can read pictures, Textures, which it takes after its input. t.sample(u, v) gives the color of texture t at u (0 left, 1 right) and v (0 top, 1 bottom). Shown, not run:

gpu.texture(width, height, pixels) makes a texture from its pixels, four numbers each: red, green, blue and opacity, row by row from the top. sample works on the CPU too, with the same colors, so this runs with no window:

  • A color from sample is blended between the four pixels nearest the spot. A spot past an edge takes the edge's pixels.
  • A texture's colors are in sRGB, as image files and screens have them, so a texture drawn as it is shows its own pixels.
  • A texture is 1 to 8192 pixels wide and high. Making one needs a GPU: with none, gpu.texture fails with a GpuError.
  • sample is the one call on a Texture a gpu fn can make, and only a gpu fragment fn takes textures.

frame.draw gives one texture for each Texture the fragment fn takes, in order, as textures:. Leaving it out is a compile error; a list of another length is a panic:

Mistakes caught when compiling

Every part of a draw is checked before the program runs. A vertex fn must give a position:

gpu.pipeline takes a gpu vertex fn and a gpu fragment fn, not plain functions:

A draw gives what the vertex fn takes. Here place takes a Camera as its second parameter, so the draw must give it as instances::

A draw can't stop the program halfway through a frame. So in a vertex or fragment fn, an overflow or a division by zero gives a wrong value for that corner or pixel, not a panic. On the CPU, the same fn panics as any other.

A pipeline is compiled for the GPU when it is made, or when a screen opens, never in the middle of a frame. The window, the screen and the frame are on GPU Screens.
