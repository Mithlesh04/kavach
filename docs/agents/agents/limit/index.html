Agents: limit

● Intermediate4 min

limit sets hard boundaries on a capability method: on each call, on totals, and on the number of calls in a window.

In simple terms

A limit works like the caps on a bank card: a cap for each purchase, a cap on the total, and how many purchases are allowed in a period of time. A call past a cap is turned down and never runs.

The kinds of rule, as spec 8.3 lists them:

RuleMeaning
amount <= 10_000Every single call must satisfy this
sum(amount) <= 50_000 per dayTotal across calls in the window
count <= 100 per dayNumber of calls in the window
held <= 8Number of calls under way at once, this one included: a call holds its place from when it starts until it returns or fails. For licence seats, GPU slots and database connections. It takes no window: held <= 8 per day is a compile error.
tokens <= 200_000 per dayIn limit Ai: the tokens (in and out) the window's earlier asks took, with those still waiting for their answer counted as the agent's settings say (below). Once they pass the limit, the next ask is refused; the one that crosses it still runs, since an answer's size is known only after it. Anywhere else, tokens is a compile error.
cost <= 5.00 per dayIn limit Ai: the US dollars the window's earlier asks cost, worked out from each model's price (8.4, *Prices*), with those still waiting counted as for tokens. The one that crosses the limit still runs, as with tokens, and the refusal of the next one says so. An ask whose list has a model with no known price is refused, never counted as free. Anywhere else, cost is a compile error.

The method's parameters are in scope by name: amount is the amount of each call. Call by call:

CallThe checksPrinted
refund(1, 400)400 ≤ 500, and the day's total 0 + 400 = 400 ≤ 700refunded 400 on order 1
refund(2, 900)900 > 500: the rule amount <= 500 is brokenrefused: Denied(reason: "limit broken: amount <= 500")
refund(3, 250)250 ≤ 500, and 400 + 250 = 650 ≤ 700refunded 250 on order 3
refund(4, 300)300 ≤ 500, but 650 + 300 = 950 > 700refused: Denied(reason: "limit broken: sum(amount) <= 700 per day")

A refused call never runs, so it doesn't count toward the totals: after order 2, the day's total is still 400.

The window is day 1, 05:00 to day 2, 05:00. It holds 3 of the calls, so a call now is refused: it would be the fourth in 24 hours. Midnight has passed, yet day 1's calls still count: nothing resets at midnight.

  • A rolling window, not the calendar. per day counts the calls of the last 24 hours before each new call, not the calls since midnight.
  • A month is always 30 days. February, a 31-day month or a leap year don't change it. For calendar months, with their real lengths, use dates: add_months.
  • No time zones, no daylight saving. Time is measured on a clock that never jumps, so a day is always exactly 24 hours, in every country.
  • Across restarts, with a state file, each call's time is saved in UTC, so the window carries on where it was.

Calls under way at once

held <= n counts the calls running right now, this one included, not the calls made. A call holds its place from when it starts until it returns or fails. Use it for licence seats, GPU slots or database connections. Here two calls run at once and each takes a while, so a third, made while they run, is refused; a fourth, made after they returned, runs:

It counts what is happening now, so it takes no window:

Calls under way end with the program, so a state file keeps none: after a restart, held starts from nothing.

A token budget for AI calls

In limit Ai, tokens counts the tokens, in and out, that the window's earlier asks took. Once they pass the limit, the next ask is refused and never sent. Here each answer takes 60 tokens in and 10 out, against a budget of 100 a day:

  • The first call starts at 0 tokens, the second at 70: both are under 100, so both run.
  • The second takes the total to 140. The third is refused with Denied before it is sent, so it costs nothing.
  • The call that crosses the limit still runs, because an answer's size is known only after it. So the total can end above the budget by one call's tokens, as it does here.
  • The tokens counted are the ones in the audit log's model: line, and with a state file they are kept across restarts, like sum and count.

Many asks at once

Many asks can run at once, one per task, and each answer's size is known only when it comes. So tokens also counts the asks still waiting for their answer. The agent's settings choose how, with asks_under_way:

asks_under_wayAn ask under way counts asSo
UnderWay.Average (the default)The average size of the window's answered asksA new ask the limit would refuse waits while others are under way, then is checked again with their real sizes. When others are under way and none in the window has answered yet, their size isn't known, so it waits for the first answer. The total passes the limit by about one answer at most, as when asks run one at a time. Near the limit, asks run one after another.
UnderWay.LargestThe most it can take: for each of its 3 tries (8.4), its prompt's length in bytes (no token is shorter than a byte) and its model's max_tokens. The new ask counts this way too.The total doesn't pass the limit, except by text the provider adds to a request, such as its own instructions for structured output. But asks are refused well before it, as most answers are much shorter than max_tokens. With the default max_tokens of 4,096, each ask counts as at least 12,288 tokens, so a smaller limit refuses every one: give the agent's model a smaller max_tokens.
UnderWay.NotCountedNothingNothing waits. 10 asks started together under tokens <= 100 per day all run, and can take 700 tokens. For a limit kept as a rough guide.

Here 10 asks start together under a budget of 200 tokens a day, and each answer takes 70 tokens. The test runs it once with each setting, in the interpreter and in native code:

asks_under_wayAnsweredWhy
UnderWay.Average3 of 10as when they run one at a time (0, 70 and 140 pass; 210 doesn't), so 3
UnderWay.Largest2 of 1093 and 186 pass, 279 doesn't, so 2
UnderWay.NotCounted10 of 10none is counted before it answers, so all 10

Under Largest, each ask counts the most it could take: for each of its tries, its prompt's length in bytes and its model's max_tokens. Here that is 3 × (1 + 30) = 93.

In Observe mode nothing waits: the limit is only reported.

The setting is chosen when the program is built, like the rest of the settings:

A money budget for AI calls

cost counts US dollars the way tokens counts tokens: what the window's earlier asks cost, worked out from each model's price (usage and cost). It is a Decimal. Here one ask costs about a third of a cent, against a budget of a tenth of a cent a day:

  • The first ask starts at $0, so it runs, and crosses the budget: a cost is known only after the answer.
  • The second is refused before it is sent. The refusal gives the cost so far and says why it can be over the budget.
  • ai.spent counts only the ask that reached the model.
  • asks still waiting for their answer count as the agent's asks_under_way setting says, as for tokens.
  • A reply that gave no token counts costs 0 here, as it takes no tokens.

A model with no known price can't be counted, so an ask that could reach one is refused, never counted as free. With claude-opus-4-1, which Kavach has no price for, each ask fails with Denied(reason: "no price for claude-opus-4-1: give one, decision 0140"). That holds for any model of a list, even when an earlier one would answer. Give the price by wrapping the provider (your own prices).

Counting a prompt's tokens with ai.count is free, so no rule of limit Ai counts or refuses it, count included.
