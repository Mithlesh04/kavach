Agent Use Cases

Also known as: examples use cases recipes shopping assistant deploy bot support triage customer service refund budget spending limit

● Intermediate8 minBefore this: Agents, ask<T>Spec 8.3

Four agents, each with a real risk and the line of code that removes it: a spending limit, a person who approves, a model that can only sort, a folder that can't be left.

In simple terms

Think of each one as a safety catch: a spending cap, a manager's signature, a multiple-choice form, a locked door. Each catch is one line of code, and every program here really runs as shown.

Each program here runs as shown, and its output is checked on every build of this site. Copy one and change it: the compiler tells you when a change would let the agent do more than it says.

A shopping assistant with a budget

An assistant buys what the user asks for. A confused model, or a tricky product page, must never empty the account.

What holds it: A limit on each purchase, on the day's total, and on purchases per hour.

The laptop is over the per-item limit; the tea would take the day past 3,000. Both refusals are errors the program handles, and both are in the audit log.

A deploy bot that asks before production

Releasing to a test server should be quick; releasing to production needs a person on call to agree.

What holds it: approve Deploy.release when env == "production" by "oncall".

Staging goes out at once. Production waits for the on-call person; in this run no one answered, so nothing was released.

A support inbox sorted by AI

Each message goes to the right team, without the model being able to do anything but sort.

What holds it: ask<Triage> can only answer with one of the three teams, and the agent can only assign tickets, at most 200 an hour, with at most 1,000 model calls a day.

Run with --dry-run: the model and the help desk are never called, and the lines show what would have been. Try a new agent this way before it touches anything real.

A file agent that stays in its folder

An agent reads documents from an inbox folder. A file name it is given, by a person or a model, must not reach anything else.

What holds it: The implementation says uses Fs.read("./inbox"): it can only read, and only there.

../passwords.txt climbs out of the folder, so the read is refused while the program runs, and the agent reports it.

A refund agent, start to finish

The repository's refund bot puts it all together: ask decides, limits cap each refund and the day's total, finance approves large ones, every call is audited, and a crash half way never pays twice.

the refund bot example

More ideas

  • An expense checker: ask reads each receipt into a typed record, and payouts above a limit go to a manager.
  • A newsletter sender: count <= 5_000 per day on Email.send, started in observe mode for its first week.
  • A database clean-up agent: it may archive rows, never delete them, because only Db.archive is in its can.

Every one of these keeps its promise for the same reason: the agent touches the world only through capabilities, and those are checked by the compiler and the runtime, not by the model. See What You Can Build for projects of every level.
