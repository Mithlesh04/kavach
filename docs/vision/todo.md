## First: speed (before any new feature)

Kavach's main promise is speed with safety. Until the benchmarks show Kavach at least as fast as C++, new features wait: building more on a slow base makes no sense.

1. **Faster than C++ on every benchmark** ([benchmarks/loops](../../benchmarks/loops/README.md)): the goal is Kavach **at least 2× as fast as C++** (`g++ -O2`, same machine), and never slower. **No new feature starts until this holds**, except what makes the benchmarks faster. Where C++'s defaults are slow (hash maps, allocation, text), 2× comes from better defaults. On a tight arithmetic loop C++ is already near the machine's limit, so there Kavach wins by doing less work: its values never alias, so it can keep data in registers and vectorize where C++ must assume pointers overlap. Each benchmark is small code on **large, heavy data**, covering all the basics:
    - loops over numbers: integers and floats, hundreds of millions of rounds;
    - big lists: building, reading, changing, summing tens of millions of items;
    - nested data: lists of lists (matrices), lists of records, maps of lists;
    - maps and sets with millions of keys;
    - single reads at a given index or key, from a large list and a large map (asked 2026-11-02: at least 20× the big dynamic languages; **both pass**, 57× and 33× Python, and 1.9× and 2.5× faster than C++, [benchmarks/lookups](../../benchmarks/lookups/README.md)). Asked again for more (2026-11-02): each random read past the caches waits on memory in every language, so the gain is in overlapping the waits. Done: prefetching in loops whose index comes from a pure recurrence (`compiler/kir/src/prefetch.rs`), lists and integer-keyed maps. Next: 2 MB pages for large lists and maps (8% in C++), and map lookups with integer keys inlined into native code instead of a runtime call;
    - records and unions: creating, reading and matching millions of them;
    - text: building, splitting, searching large text;
    - sorting large lists; recursion and function calls; closures.

    Fix what is slow in the compiler and runtime first (call overhead, list access, reference counting), then add the LLVM backend for release builds if Cranelift can't get there.

    **Where it stands (2026-11-02, [results](../../benchmarks/loops/README.md#results)):** faster than C++ on every benchmark: `closures` 12× (its fused sum pipeline runs on all cores), `loop` 30× (its modular accumulation is a sum in disguise, on all cores), `sort` 10× (its buckets sort on all cores), `records` 3.2×, `lists` 3.0×, `matrix` 2.1×, `text` 1.7×, `maps` 1.4×, `fib` 1.2×; even on `floats`, where every round waits for the last multiply and add, for any compiler. All build through the LLVM backend ([decision 0018](../decisions/0018-llvm-backend-through-llvm-tools.md)), which now builds every conformance test and example. 2× everywhere still needs: `lists` and `text`, where most of the time left is the kernel zeroing fresh memory pages (C++ pays it too; using less memory per item is the way out), `matrix` (AVX2 would help it, but targeting AVX2 made `loop` 40% slower), and `fib`, where calls are already as cheap as C++'s. **Measured again 2026-11-09** at commit b65b7ae7, three rounds ([results](../../benchmarks/loops/README.md#results)): `text` is now 2.0× (0.51), `matrix` 1.9×, `records` 2.6×, `lists` 2.5×, `closures` 4.9× (C++ ran faster that day: 98 ms, not 311), `maps` 1.4×, `sizedmaps` 1.6×, `fib` 1.2×, `floats` level. Measured from its first ratio, `lists` is now 9.2× better (3.78 → 0.41), under the 10× of the target below, as C++'s own time fell from 189 to 74 ms between the two days.

    Two targets inside this item:
    - **Plain `for` loops at least 3× as fast as C++, C# and Go.** Holds against C++ (3–28×); C# and Go are not measured yet. The machine's speed is the same for all of them, so the gain must come from doing less work: proven value ranges remove overflow checks and turn `%` into a compare and a subtract, divisions by constants become multiplications, and loops without aliasing are vectorized.
    - **At least 10× faster than each benchmark's first measurement** (the "Kavach got faster by" column in the [results](../../benchmarks/loops/README.md#progress)). Done for every benchmark. Only changes that help real programs count, never rewriting a benchmark's loop into a formula. All ten are done: `loop` closed it when its modular accumulation was recognized as a sum and spread over the cores; `sort` by sorting its buckets on all cores.
    - **Math on large data at least 20× as fast as C++** (`g++ -O2`, one thread): sums, products, dot products, element-wise arithmetic, `sqrt`/`pow`/`sin` over big lists and matrices. A single operation can't beat C++ (both compile `a * b + c` to the same one or two instructions), so the gain comes from doing many at once: SIMD (4–8 numbers per instruction, AVX2/AVX-512) and all cores (values never alias, so a loop over a big list splits safely across threads; overflow checks still panic at the same place by re-running a chunk that overflows). Results must be exactly those of the plain loop; floating-point sums keep their order unless the program asks for a faster, reordered sum. The [math benchmarks](../../benchmarks/math/README.md) exist, and every one beats C++. Element-wise loops and integer sums now run on all cores over a kept worker pool ([decision 0031](../decisions/0031-loops-on-all-cores.md), landed 2026-11-02: `scale` 0.60× → 0.37×, `sum` 0.82× → 0.35× of C++, combining partial sums exactly — stored prefix bounds catch any overflow the plain loop would panic on). Float reductions keep their adding order, so `dot` waits for an asked-for reordered sum; wider SIMD is the other half of 20×. Tasks on all cores are in place ([benchmark](../../benchmarks/tasks/README.md)); the rest of item 1 is at the limits listed above, and work moved on (2026-10-31).
    - **JSON at the speed of simdjson** (C++, several GB/s). The [JSON benchmark](../../benchmarks/json/README.md) (52 MB) shows Kavach 4.2× as fast as Python overall (2026-11-08): `stringify` 6.5×, `decode<T>` reads straight from the text (6.3×), `parse` 1.4× faster than Python's C parser, reading fields 1.5× slower. simdjson's speed needs a compact layout: one buffer per document (a "tape"), with `Json` values pointing into it, instead of an object per value; then SIMD for finding strings and structure. Every place that matches a `Json` in native code changes, so it got a decision record, [0032](../decisions/0032-json-on-a-tape.md) (2026-11-02); the tape lands first, then the SIMD structural pass. Waits, like the math target, for the SIMD work.
    - **A hash algorithm of our own for maps and sets**, compared with the ones in use today (SipHash, FxHash, wyhash, aHash, Swiss tables): seeded per run so attackers cannot force collisions, and faster than C++'s `std::unordered_map` by at least 2×. Done but the 2× ([docs/architecture/hash-maps.md](../architecture/hash-maps.md)): seeded, an adaptive integer hash, key-and-value buckets. Measured 2026-11-02 (WSL, 2M integer keys): inserting 45–68 ms against C++'s 54–60, looking up 8–11 ms against 6–7. The gap to 2× is growing: a map given its final size up front is exactly 2× (41 ms against 82). Writing each entry twice is not the cost; five changes were measured and none shipped ([hash-maps.md](../architecture/hash-maps.md#open-questions)). `Map.with_capacity(n)` landed (2026-11-02): a map told its size is 1.6× C++ given `reserve` ([sizedmaps](../../benchmarks/loops/README.md#results)), 2× C++ without. An integer index now doubles in place (2026-11-09: insert phase best 63 → 57 ms). A profile shows what 2× needs: a smaller index or an insert generated inline, since even a map that never grows takes about 45 ms against the 44 that 2× allows ([hash-maps.md](../architecture/hash-maps.md#open-questions)).

    - **The everyday operations 20× or more** (Mithlesh, 2026-11-01): the same push on what every program does all day, not only arithmetic — function calls, callbacks (calling through function values held in records or passed in, as `sort_by`, servers and C callbacks do, and callbacks nested in callbacks, a handler wrapping a handler, as middleware does), assignment and copies, conditions and branching, memory management (allocation, reference counting, freeing), the call stack itself (the per-call stack check, deep recursion, the stacks tasks and callbacks run on), pipelines (chains of `map`, `filter`, `sum`, and tasks passing values on), and compiling itself. **Chained calls at least 20× the big-market languages** (Mithlesh, 2026-11-01): data chains, builder chains as transaction APIs write them, and chains nested in chains, measured against Python and Node directly ([benchmarks/chains](../../benchmarks/chains/README.md)) — the fluent style blockchain and web companies live in. Kavach's edge is doing less work: chain stages fuse into one loop with no list between them, and a builder chain on an unshared record can change it in place. **Where it stands (2026-11-01, [results](../../benchmarks/chains/README.md#results) and [everyday](../../benchmarks/everyday/README.md#results)):** scalar replacement (`compiler/kir/src/sroa.rs`) now keeps unshared records and fixed-size lists in registers: `copies` went from 89× slower than C++ to even, `alloc` from 5.9× slower to 31× faster, `stacks` from 5.9× to 1.6× (an adding recursion becomes an accumulator loop, `compiler/kir/src/unrecurse.rs`), `callbacks` from 1.2× slower to 0.87 — faster than C++ (a once-stored callback devirtualizes and inlines, `compiler/kir/src/devirt.rs`), and `builderchain` from 62× slower to even — vs Python it is 5463×, the 20× bar beaten by 270×. Chains written as one fluent expression (and chains nested in chains) now hoist into one stage per `const` and fuse into a single loop (`compiler/kir/src/fuse/hoist.rs`): `datachain` 64× Python and 2.4× faster than C++, `nestedchain` 46× Python — every chain beats the 20× bar. Each gets a benchmark in [benchmarks/](../../benchmarks/README.md) with its number recorded, like the loops and math sets. Against C++ the honest wins come from doing less work — inlining calls away, fusing pipeline stages so no list between them is ever built, allocating from pools, dropping checks a proof covers — because a single call or branch is already at machine speed; 20× in full shows against the dynamic languages, and those comparisons get published too. Compile speed folds in the "builds under 0.2 s" note below: `kavach build` of hello world is ~0.26 s today, nearly all linking.

Kavach gets no cron jobs and no wait until a time of day, as the standard libraries of Java, Go, Python, JavaScript and Rust have none (Mithlesh, 2026-11-04: do as others do; decision 0062): a job at a time of day belongs to the operating system's scheduler. 3. **Network waits faster than C++** (Mithlesh, 2026-11-03: "at any cost we have to speed up Kavach"): the I/O event loop (decision 0046) made 10,000 TCP round trips between two tasks take 0.43 s on Linux and 0.6 s on Windows, against 0.3 s for C++ with blocking sockets ([benchmarks/net](../../benchmarks/net/README.md)). Done 2026-11-03: only the next task's thread wakes, and it spins a moment first (`runtime/core/src/tasks/turns.rs`): Linux 110 ms, 2.8× faster than C++ (`channels` too: 303 → 79 ms, 6× C++). Windows is 470 ms against Python's 390: each socket call costs more there, and a wait makes two (a try that would block, then the queue). TLS on the queue too (2026-11-03): 2,000 round trips 63 s → 0.23 s on Windows; a TLS write no longer holds the turn. UDP and connecting on the queue too, and TLS handshakes while accepting no longer block (2026-11-03). **The big gap left: many connections at once** ([benchmarks/net](../../benchmarks/net/README.md#many-clients-at-once-clients)): 100 clients × 1,000 round trips take Kavach 5.5 s, C++ 93 ms on all cores and 345 ms on one. Tasks take turns on operating-system threads, and with many tasks each turn wakes a sleeping thread on another core. Mithlesh chose both (2026-11-03, [decision 0048](../decisions/0048-tasks-as-coroutines-per-core.md)): tasks as coroutines through `corosensei`, then on every core. In this order: coroutines on one thread in native code; tasks on all cores (own heaps); coroutines on every core. Also left: QUIC on the queue (no local QUIC server to test against yet), and fewer calls per wait on Windows (completion-based IOCP reads instead of `mio`'s readiness). Goal: faster than C++ on every network benchmark, then a server under load (many connections) measured against C++, Go and Node. Profiled 2026-11-04 (`docs/architecture/tasks-on-all-cores.md`): the channel's cost is the system call that wakes a sleeping worker, once per item (12 µs in WSL; native Windows is nearly level with one core). Next: tasks that move to the waker's worker, as Go's do (coroutines that move between threads, memory freed back to its own pool, no thread-local kept across a wait). Looked at 2026-11-04: the pool is no obstacle (its blocks are never freed, so an object freed on another thread can join that thread's free list); the obstacle is any thread-local address LLVM works out once and reuses after a wait, in generated code and in the Rust runtime alike, which needs an audit before a coroutine may move. The gap is mostly WSL's 12 µs wake-up: native Windows is 250 ms against 200 on one core. On one core (2026-11-05, [benchmarks/net](../../benchmarks/net/README.md#many-clients-at-once-clients)): 100 clients × 1,000 trips take 0.72 s against C++'s 0.48 s on one core, with the same system time: 1.25 µs of user time a round trip, spread over the wait path (no hot spot), so the next step is a shorter wait path as a whole. All cores, profiled 2026-11-06 ([what was found](../architecture/tasks-on-all-cores.md#measured-so-far)): 100 clients × 1,000 trips take `spawn cores` 257 ms, plain `spawn` 629 ms, C++ 108 ms, about 2.2× behind at every core count. Workers no longer spin before sleeping (the spin never saw sockets: one connection 1,165 → 896 ms), and sockets no longer go through one locked table. Left: two system calls a wait makes that a blocking read doesn't (1.6 µs a wait on one core), system time on all cores 3× C++'s, and a thread for each `net.connect`. Done 2026-11-07: a worker looks at its sockets for up to 100 µs before it sleeps ([measured](../architecture/tasks-on-all-cores.md#measured-so-far)): 100 clients × 1,000 trips went from about 2.5× C++ to about 1.4×, with less CPU; 1 client from 2,400 ms to 320 ms, against 2,100 ms for blocking C++. The look gives up when it keeps finding nothing, so it costs a slow server nothing, and plain `spawn` looks too (1 client from another program: about 2,200 → 650 ms, against about 2,100 ms for C++). Left: `net.connect`'s thread for each name lookup; a read that finds nothing and `epoll_wait` on each wait; plain `spawn` with many busy clients stays on one core by design.
4. **GPU pipelines: data that stays on the GPU** (Mithlesh, 2026-11-03, for games and other work that can't afford copying data back and forth): done so far, a list a GPU `map` read or made stays in GPU memory, so the next `map` of it skips the copy over (spec 15.2), and `map`s chained in one expression run as one kernel (2026-11-03: 10 million items, 51 → 25 ms). Results kept in a variable stay on the GPU until the CPU reads them (2026-11-04, decision 0055: 10 million items mapped 100 times, 1,900 → 530 ms). Whole-number `sum`, `min` and `max` on the GPU end such a pipeline with only the result copied back (2026-11-04, spec 15.2). `filter` too, its kept items in order and left on the GPU (2026-11-04). Done 2026-11-04: a `gpu fn` takes and gives records and tuples (spec 15.1), so a game's frame is one `map` of the last frame's list, which stays on the GPU: 1 million particles × 300 frames in 352 ms ([benchmarks/gpu](../../benchmarks/gpu/README.md#frames-records-that-stay-on-the-gpu)), against 330 ms for C++ on one core. Done 2026-11-04: frames don't wait for each `map` (decision 0061, Mithlesh's choice: a panic shows at the next read); most of the time left is opening the GPU, about 235 ms once per program, and the frames take 0.23 ms each (measured after a first frame). Opening is the driver's own work (Vulkan 160 ms, the device 40), already started with the program on another thread. CUDA does the 300 frames in 17 ms (benchmarks/gpu/cpp/frames.cu): it writes in place, so the particles stay in the GPU's cache. Done 2026-11-04: result buffers no list holds any more are reused, with no zeros to write first (`runtime/gpu/src/spare.rs`), and `ps = ps.map(f)` writes in place on the GPU when nothing else holds `ps`: with both, 300 frames after the first take 70 ms (190–200 before; CUDA 17). Next, in this order (Mithlesh's decisions: invisible, no `GpuList` type; float sums keep their order): the 30 ms of the frames' 70 outside the kernel (found 2026-11-05: the final read of the list, 16 MB back and 4 million fields converted; 19–22 → 12–21 ms by converting item by item; the rest is the copy and the list's fresh pages), then a record of four 32-bit fields read as one `vec4` in the kernel (19–22 ms by hand; done 2026-11-04, 5–20% faster side by side); reusing the count and stop buffers took 1,000-particle frames from 20 to 11 ms in a timing-only test; and a CPU `map` of records 12× slower than C++. Done 2026-11-04: a lambda's record result goes into the list field by field, its parameter reads the item in place, and functions that take or give records are inlined up to 120 expressions (11.4 → 4.1 s for the benchmark's 300 frames); `ps = ps.map(f)` now writes each item in place (2026-11-04): numbers (1M `Float32` × 300 frames: 1.15 → 0.24 s) and records, set field by field (the frame loop's lambda: 3.9 → 0.78 s, 2.4× one C++ core); a `map` that may run on the GPU does it in place too when the CPU does it (4.1 → 0.84 s with the GPU off): its branch takes the list out of the local once, since each read of a local the GPU may hold fetches it (`gpu_stay.rs`). **Streaming data through the GPU** (Mithlesh, 2026-11-03: data arriving from the network, files or an API, worked on in chunks, without waiting on copies): (1) numbers read from `Bytes` with no copy (a chunk from `fs.chunks` or a socket seen as `[Float32]`, today only `b.to_list()` to `[UInt8]`); (2) copies that overlap the work: while the GPU works on chunk n, chunk n+1 goes over and chunk n−1 comes back (double buffering, pinned memory), so a loop over chunks runs at the speed of the slower of the disk, the bus and the GPU; (3) sums and other reductions across chunks kept on the GPU until the end. Mithlesh chose invisible, as PyTorch's data loader overlaps by itself ([decision 0067](../decisions/0067-streaming-data-through-the-gpu.md), Accepted 2026-11-05), with a `kavach check` note for a loop that isn't overlapped; measured on a file larger than GPU memory against C++ with CUDA streams. Part (1) done 2026-11-07: `b.as_list<Float32>()` reads any `Bytes` as numbers (spec 2.13). It is one bulk copy per chunk, with no work per item, not yet the view the decision asks for: a list owns its buffer, so a true view touches every list operation, and it should be measured first. Part of (2) done 2026-11-07: `fs.chunks` reads the next piece of 1 MB or more on a helper thread ([measured](../../benchmarks/gpu/README.md#streams-a-file-bigger-than-a-chunk): 2 GB in chunks, read and `as_list` 1.6× faster, with a `gpu fn` about 1.3×). Parts (2) and (3) done 2026-11-07 (Mithlesh's choice: build it): a loop's `total += xs.map(f).sum(g)` doesn't wait for each sum, the statement running later, in order (spec 15.2, `compiler/kir/src/gpu_later.rs`), with `kavach check` saying which loops wait and why ([measured](../../benchmarks/gpu/README.md#sums-a-loop-doesnt-wait-for): 2 GB of light work 3.4 → 1.3 s, heavy about 8 → 2.8 s, and level with CUDA once the disk sets the speed). Done 2026-11-08: a chunk nothing else holds becomes its list with nothing copied, and kernels divide through unsigned numbers (200 steps 4.4 → 2.7 s). Done 2026-11-08: uploads of 1 MB or more go through two staging buffers of our own, used in turn, as `write_buffer` made a new 64 MB one every few chunks (1-step stream about 1,250 → 1,040 ms; the copy itself is the trip over the bus, as CUDA's is). Left: with the file in the system's cache CUDA is still about 1.8× ahead on 1 step (before that change; mostly opening the GPU, which CUDA's timer leaves out) and 2.6× on 200; past 200 steps the kernel is the limit (a kernel whose loops surely end goes without `wgpu`'s counter in each loop since decision 0077: 800 steps 6.0 → 4.9 s, against CUDA's 2.2); `as_list` as a view when the chunk is still held; network chunks.

New module features are written in Kavach inside the module (as `std.http`'s JSON calls are). Places that cross the line today, to move behind a small, stable set of runtime primitives: built-ins only modules may call (`log_write` for `std.log`, `test_random` for `std.test`), and standard functions handled by name in the core (`compiler/kir/src/lower_std.rs`, `compiler/interp/src/std_lib.rs`, `std_time.rs`, `net.rs`).
- **Builds under 0.2 s** ([decision 0024](../decisions/0024-pay-only-for-what-you-use.md)): a "hello world" `kavach build` takes about 0.26 s (2026-11-01, Windows, release compiler), of which linking is about 0.25 s: the linker reads the whole runtime archive (74 MB with thin LTO). Ideas: a smaller archive (no debug information, no bitcode), linking a prebuilt object of the runtime's core, or a linker that caches. `rust-lld` was no faster. Measured again 2026-11-09 (release compiler, the archive now 190 MB): Windows 0.74–0.77 s warm. Linux (WSL, on ext4) 0.39–0.46 s, of which GNU ld takes about 0.42 s; rustup's `lld` (`cc -B…/gcc-ld -fuse-ld=lld`) links the same in 0.14–0.17 s, but its program keeps twice the code (1.15 MB stripped against 0.58 MB, `-z start-stop-gc` and `--icf=all` change nothing), which would break the size budget. Why (2026-11-09, link maps of hello world, LLD 23.1): lld's code is smaller (`.text` 405 KB against 413), but it keeps the exception tables (`.gcc_except_table`) of 11,092 functions when only about 300 of those functions are in the program: 600 KB against GNU ld's 12 KB. Switching needs those tables dropped with their functions, which lld's own garbage collection doesn't do for the runtime's objects. On a Windows drive seen from WSL (`/mnt/d`, `/mnt/e`) every link takes 7–8 s: the archive is read through the file share.
- **Logging, the rest** (spec 14.12, `stdlib/log/log.kav`, `runtime/core/src/log.rs`): sampling (keep one event in N of a type), and Kavach Link as a pipeline, with the Kavach Link item.
- **Linux executables carry Rust's backtrace printer** (`gimli`, `addr2line`, `miniz`, about 200 KB), so "hello world" is 500 KB there, not under 300 KB: the standard library's panic hook links it, and only a nightly `build-std` with `panic_immediate_abort` leaves it out (decision 0024).
- **Test suites flake when both platform halves run at once** (2026-11-01): running the Windows and Linux (WSL) `cargo test` suites in parallel on one machine makes about one test per batch fail with a timeout or a file-not-found (`tools/cli/tests/ai.rs`, `conformance.rs`, `native.rs`, and timing-based conformance tests such as `09-concurrency/parallel-map-keeps-order-and-limit.kav`); each passes alone. Likely disk and CPU contention around spawned `kavach` processes. Ideas: longer timeouts under load, retry a spawn that can't find its file, or stagger the halves.
- **Memory-mapped files as an explicit API** for storage engines (item 5), not behind `fs.read_bytes`: measured 2026-11-02 (WSL, 1 GB, file cached), `read_bytes` takes 186 ms (C++ reading into a vector, 228 ms), mapping and touching every page 33 ms. But while a file is mapped, another process's writes show through and a truncation crashes the reader (SIGBUS), so a `Bytes` value would no longer be a value. Only code that asks for a mapping, knowing this, should get one. Every `Bytes` operation goes through `rt_bytes::with_bytes`, so a mapped variant of `Data` is a small change there.
- **File I/O through io_uring/IOCP**, so a task waiting for a file lets the others take their turns: comes with the event loop of the networking item.
- **Pipelines computing ahead:** a task computes ahead of its turn only until its first effect; a `take`, compute, `put` loop needs a rule that keeps output the same ([spec 9, open questions](../spec/09-concurrency.md#open-questions), [decision 0020](../decisions/0020-tasks-take-turns.md)).
- **Connecting to a closed port takes about 2 seconds on Windows** (the system retries); the conformance tests avoid it.
- **HTTP/3, the rest** (`stdlib/http/h3.kav`, `runtime/net/src/net/quic.rs`, [decision 0022](../decisions/0022-http2-and-http3.md)): servers (they need TLS servers first); `http.get` choosing HTTP/3 on its own when a server announces it with `alt-svc` (needs state kept between requests); POST and other methods over HTTP/3; several requests on one connection; QPACK's dynamic table.
- **HTTP/2, the rest** (`stdlib/http/h2.kav`): a server answers one connection's requests one at a time (streams could each get a task); a client opens a connection per request (no reuse); HPACK never uses Huffman codes or the table when encoding; `https://` servers need TLS servers first.
- **TLS, the rest** ([decision 0021](../decisions/0021-tls-through-rustls.md), `runtime/net/src/net/tls.rs`): the system's root certificates as an option; a way for a server to see who a client is (its certificate's name, after mutual TLS); and a TLS listener's handshake runs while accepting, so a slow client holds `accept` (and its task's turn) up to the deadline.
- **Tests that need the internet** don't run by default: `cargo test -p kavach-cli --test online -- --ignored` (`tools/cli/tests/online.rs`).
- **A time limit on any call that waits inside** (`download(url).timeout(5.seconds)`): needs the call's work cancelled ([spec 9, open questions](../spec/09-concurrency.md#open-questions)).
- **`Bytes` in JSON** ([spec 2, open questions](../spec/02-types/README.md#open-questions)).
- **Duration arithmetic** (`a + b`, comparing durations): `Duration` is a record with `ms` for now (`stdlib/time/time.kav`).
- **A folder from a value** in `uses Fs(…)`, and narrower `Net(…)` ([spec 8, open questions](../spec/08-capabilities-and-agents/README.md#open-questions)).
- **C, the rest** (spec 10.7, `compiler/kir/src/lower_ptr.rs`): structs passed by value, variadic functions (`printf`), pointer arithmetic and casts between `Ptr` types.
- **Text from C on Windows** is often in the ANSI code page, not UTF-8 (`getenv` gives `é` as one byte), so `p.text()` panics on it; a way to read such text (and to pass text that way) may be needed (`runtime/native/src/rt_ptr.rs`).
- **`ask<T>` can't answer with a map or a tuple**: structured outputs need every object closed (`additionalProperties: false`), so a map has no schema; today `ask` stops with a clear message before calling. A map could travel as a list of key-value records (`compiler/interp/src/ai.rs`).
- **Refreshing the `kavach context` index** (spec 13.9) as files change, from the language server or `kavach check --watch`, file by file.
- **Colors in the old Windows console** (conhost without virtual terminal mode) show as escape codes; turning the mode on needs a system call, and `unsafe` is allowed only in `runtime/native` while `kavach run` prints from the interpreter. Also background colors ([spec 14, open questions](../spec/14-standard-library/README.md#open-questions)).

## Later: Phase 3 and beyond

5. **For database companies:** everything a storage engine needs, fast and safe ([platform](platform.md#databases-and-storage-engines)): direct I/O and `fsync` control (`fs.write_durable` done: atomic replace forced to the disk, file and folder, spec 14.3), memory-mapped files, checksums (`b.xxhash64()` done, XXH64 at the reference implementation's 13 GB/s; `b.crc32c()` done, hardware CRC32C at parity with C++ — 64 MB in ~10 ms both sides, [benchmarks/bytes](../../benchmarks/bytes/README.md); byte-packed lists are done, [decision 0030](../decisions/0030-byte-packed-lists.md), with pushes in counted loops hoisted into room reserved up front: the whole build-and-checksum run went 8.2× → 1.29×: packed lists, hoisted pushes, a proven-fit conversion check removed so the stores vectorize, and `Bytes(list)` copying whole words), SIMD, atomics and lock-free structures, custom allocators and arenas, zero-copy binary formats, predictable latency (no GC), encryption at rest, crash-recovery testing with deterministic simulation and fault injection (started: generated tests' fake disk is full for some paths, spec 11.5; next: a crash in the middle of a write, and torn writes, for code that must recover).
6. **For gaming companies:** steady frame times and real-time work ([platform](platform.md#games)): no GC pauses, data layouts for many entities (struct of arrays), SIMD vector and matrix math, GPU rendering (not only compute), audio and input, deterministic simulation for lockstep and rollback netcode, hot reload while the game runs, and safe mod scripting limited by capabilities.
6. **For semiconductor companies** (chip design, verification, simulation, fab data): billions or trillions of items and heavy math with accurate floating-point numbers, fast and exactly repeatable ([platform](platform.md#semiconductors-and-large-scale-computing)): data larger than memory (streaming, memory-mapped and columnar files), compact layouts (bit vectors, bit-packed lists, struct of arrays), SIMD and all cores with results identical to the plain loop, GPU offload, accurate floating point (every operation correctly rounded as IEEE 754 says, no silent fast-math reordering, compensated sums such as Kahan's and exact dot products when asked, `Float128` or double-double precision, rounding modes, interval arithmetic for error bounds, exact `Decimal`), deterministic floating-point reductions, 128-bit and big integers, fixed-point and complex numbers, compact graphs for netlists, checkpoint and restart for long jobs, work split across a cluster, calling C/C++/Python libraries, and benchmarks on billions of items to prove it.
7. **For infrastructure companies** (cloud, networking, DevOps tools): software that runs for years on many machines ([platform](platform.md#infrastructure)): single static binaries with fast start and small memory, graceful shutdown and OS signals, metrics, logs and traces (OpenTelemetry), cross-compiling for every target, containers and Kubernetes, sandboxed plugins, and supply-chain security (signed packages, a bill of materials, `kavach audit`).
8. **For web backend developers** (who use Node.js, Flask, FastAPI and the like today): web services and APIs ([platform](platform.md#web-backends)): routes from typed functions, with requests parsed and checked from the types; middleware; PostgreSQL, MySQL and SQLite with connection pools, migrations and typed queries; cookies, sessions, uploads, static files, escaped templates, WebSockets, background jobs; OpenAPI generated from the types; `kavach run --watch`; one executable to ship.
9. **Kavach Link:** the native, encrypted, typed protocol over QUIC ([platform](platform.md#kavach-link-native-networking)).
10. **Threads and processes:** `std.process` (no shell, no injection), multi-process programs talking over Kavach Link.
11. **GPU compute and pipelines:** `gpu fn`, typed buffers and pipelines, SPIR-V through Vulkan, Metal and DirectX 12.
12. **Embedded and microcontrollers:** the `no_heap` profile for ARM Cortex-M and RISC-V, board packages.
13. **For operating systems and hardware software** ([platform](platform.md#operating-systems-and-hardware)): the operating system's everyday APIs behind capabilities (clipboard, notifications, file dialogs, signals, services and daemons); system calls, memory mapping and `ioctl`; devices (USB, serial, Bluetooth, GPIO, I2C, SPI, PCI, DMA, memory-mapped registers); kernels and bare metal (a freestanding profile, interrupt handlers, inline assembly, drivers and kernel modules).
14. **LLVM backend** for optimized release builds; the public **benchmark suite** that proves the speed targets ([decision 0017](../decisions/0017-native-platform-and-speed-targets.md)); macOS and ARM64.
15. **Phase 3 tools:** package manager and registry (`kavach add`), `kavach fix`, `kavach audit`, `kavach api check`, workspaces, `--changed` builds and tests, Python and JavaScript interop.
16. **User interfaces:** `std.ui`, rendered on the GPU; desktop first, then web (WASM) and mobile (Phase 4).
