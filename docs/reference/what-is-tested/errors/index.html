What Is Tested: Errors

● Intermediate5 min

The conformance tests of spec chapter 5, Errors, by section.

38 tests: 19 check that it works, 19 that wrong use is refused.

5 Errors

RuleSpecChecksTest
The result of a call that can fail must be handled with try, catch or match.5refused: compile errorerrors-cannot-be-ignored

5.1 Declaring errors

RuleSpecChecksTest
fail returns an error of the type the signature lists after !; a value of another type is an error.5.1refused: compile errorfail-gives-the-declared-error-type
A function that can fail takes and returns values of any size like any other function: its arguments arrive whole, and it gives either its whole value or its error.5.1, 5.2, 3.1worksfunctions-that-can-fail-take-and-give-any-values
Error types are ordinary types: a function can fail with an Int or a Float, and try, catch and main treat it as any other error.5.1refused: exit 1errors-can-be-any-type
fail returns an error; catch value uses a default instead.5.1worksfail-and-catch-default

5.2 try: pass the error on

RuleSpecChecksTest
a built-in method given a function that can fail can fail with its error, and stops at the first one; a function that handles its errors inside can't fail.5.2worksbuilt-in-methods-pass-a-functions-error-on
a call that fails keeps its error when one of its arguments holds a try deeper inside, as check((try fetch(n)).items), whether it calls a function, a function value or the standard library.5.2workstry-deep-inside-an-argument
try only works when the callee's error is part of the caller's error type.5.2refused: compile errortry-needs-a-matching-error-type
try returns the error to the caller when a call fails.5.2workstry-passes-errors-on

5.3 catch: handle the error here

RuleSpecChecksTest
A call's catch handles only the call's own error: a fail or try in its arguments leaves the function.5.3worksa-calls-catch-handles-only-its-own-error
A catch handler is code of the function, not a lambda: it can change the variables around it, and a change made before it leaves with continue stays.5.3worksa-catch-handler-changes-the-variables-around-it
A catch name may reuse an outside name: it hides it inside the handler only, and the outside one is unchanged after it.5.3, 1.4worksa-catch-name-hides-an-outside-name
The name a catch gives the error belongs to its handler: using it after the handler is an unknown name.5.3, 1.4refused: compile errora-catch-name-is-only-inside-its-handler
In a function that gives nothing, a catch handler may end it with return of a call that gives nothing, such as print.5.3, 3.1worksa-handler-may-return-a-call-that-gives-nothing
An error bound to a name in a handler or a match arm can be kept after it, in an outside variable or list: it is a value like any other.5.3, 5.4, 6.1worksan-error-kept-from-a-handler-outlives-it
A catch handler may leave instead of giving a value: return from the function, or continue and break in a loop.5.3workscatch-handler-can-leave
catch e => { … } runs code with the error and gives a value.5.3workscatch-with-handler

5.5 The Error catch-all

RuleSpecChecksTest
Error(message) makes an error that is only its message: printing it prints the message, and main returning it prints error: <message> and exits with code 1.5.5refused: exit 1error-with-a-message
When main returns an error, the program exits with code 1.5.5refused: exit 1main-error-exits-with-1
A match on an Error names variants with their type and ends with _; an arm matches the error's type and variant, through any context.5.5worksmatch-on-an-error-names-its-type
A match on an Error must have a _ arm, since an Error can hold any type.5.5refused: compile errormatch-on-an-error-needs-a-catch-all
A variant pattern on an Error names its type: NotFound(path) alone is an error, since an Error belongs to no single type.5.5refused: compile errormatch-on-an-error-needs-the-type-name

5.6 Panics

RuleSpecChecksTest
checked_add returns none on overflow.5.6workschecked-add
Integer division by zero panics.5.6refused: panicdivision-by-zero-panics
panic("message") stops the task with that message.5.6refused: panicexplicit-panic
An out-of-range index panics.5.6refused: panicindex-out-of-range-panics
Integer overflow is always checked and panics.5.6refused: panicinteger-overflow-panics
Overflow in a loop panics for the values that overflow it, even where other values run without a check.5.6refused: panicloop-overflow-panics-for-a-large-multiplier
A write past a list's end panics when the loop reaches it, after the writes and output before it.5.6refused: panicloop-write-panics-at-its-index
Dividing a sized integer's smallest value by a constant -1 panics with an overflow, as any overflow does; % by -1 gives 0.5.6refused: panicnarrow-division-overflow-panics
panic(message) may compute its message while the program runs; it is printed with the panic.5.6refused: panicpanic-with-a-computed-message
Running out of memory is a panic: repeat asking for more than 1 GB of text stops the program with exit code 101.5.6, 5.8refused: panicrepeat-asking-past-1-gb-panics
Repeating empty text gives empty text, however many times: it asks for no memory, so it is not refused and ends at once.5.6, 14.2worksrepeat-of-empty-text-asks-for-no-memory
wrapping_add wraps around instead of panicking.5.6workswrapping-add
Running out of memory in a task is a panic of that task: .wait() fails with panicked: …, and the program goes on.5.6, 9.1worksan-out-of-memory-panic-stops-only-its-task
