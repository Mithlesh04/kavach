HTTP: Serving

● Intermediate4 min

A server is one function from Request to Response. Route by r.method and r.path; answer with http.text or http.json_response.

In simple terms

A server is like a shop counter: each customer brings a request, and you hand back an answer. You look at what they ask for and where, then decide what to give them.

  • Each connection runs in a task of its own, so one slow client doesn't hold up the others.
  • The status says what happened: 200 found, 201 made, 404 not found, 400 a bad request.

Who sent it

r.peer is the address of whoever opened the connection, for limits per client. A request made by hand has "":

Behind a proxy, peer is the proxy's address. Trust an address the proxy forwards in a header only when the request came from a proxy you list.

With mutual TLS, r.client_cert holds the names on the client's certificate, for allowing callers by name, and none otherwise. See TLS.

Headers

Headers are a list of Header(name:, value:), in the order they are sent, names in lower case. A name may come more than once: two set-cookie lines stay two headers.

  • r.header(name) gives the first value of a name, or none. The name can be in any case.
  • r.headers_named(name) gives every value of a name, in order.

Limits

A server faces clients that are slow, large or hostile, so http.serve holds each one to ServeLimits. Every field has a safe default, so http.serve(listener, handler) is already protected. Change only the ones you need:

  • A request that breaks a limit gets its status and the connection is closed. The handler never sees it.
  • A client that sends its headers a byte at a time holds a task for at most header_timeout.
  • A request with expect: 100-continue gets 100 Continue once its size is known to fit, before it sends the body.
  • A 503 says retry-after, so well-behaved clients wait before trying again.

Stopping

On Ctrl+C or SIGTERM (how Docker and Kubernetes stop a container), http.serve answers new connections with 503, closes those waiting for their next request, and finishes the requests under way, for at most drain_timeout. Then the program ends, without cutting a response off. A second signal ends it at once. See When a program stops.

A client that leaves

While a request is answered, http.serve keeps reading its connection. When the client closes it, the handler's task is cancelled, so a request nobody waits for stops using the server. A handler that panics gets 500, and the server goes on.

tested

Large bodies

A body up to buffered_body (1 MB unless you say) is read whole into r.body. A larger one is left for the handler to read as it comes, a piece at a time, with r.read_body(), which gives none once it has all come. An upload of any size then needs no more memory than a piece:

  • The 5-byte body fits in buffered_body: 100, so it is all in r.body, and read_body has nothing more.
  • The 3000-byte body is not in r.body: the handler reads it with read_body.
  • A read fails with a NetError when the client goes away during the upload.

Sending a file

http.file(path) answers with a file as it is read, so a file of any size is sent without being held in memory. Its content-type comes from the file's extension, and its content-length from its size:

To send something else as it is read, give a Response a reader from fs.chunks as its stream: Response(status: 200, headers: [], body: Bytes([]), stream: reader).

Forms with files

An HTML form with files sends a multipart/form-data body. http.form(r) reads it a part at a time, and each part's data as it comes, so a large upload is never all in memory:

WrittenGives
form.next() -> FormPart? ! HttpErrorThe next part, or none after the last; data of the part before not read yet is skipped
part.name, part.filename, part.content_typeThe field's name, the file's name (String?, none for a plain field) and its content-type (text/plain when not given)
part.read() -> Bytes? ! HttpErrorThe part's next piece of data, or none at its end
part.text() -> String ! HttpErrorThe rest of the part as text: for small fields

A form that isn't multipart/form-data, has no boundary, or is cut off fails with BadMessage.
