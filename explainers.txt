# Kavach explainers, step by step

> The Kavach course shows how code runs on the machine as animations:
> the CPU, RAM, the stack, the heap, the OS. Here is each one as text:
> a very short "caveman" summary, the code (a sample checked against a
> real run), and every step with the line it runs and what happens.

## Part 1: Basics

### [print: a line is built, then written in one go](https://kavachlang.com/docs/basics/output/print/#scene-print)

Caveman says: Print make whole line first, in memory. Number turn into digit. Line end with newline. Then whole line go to OS. OS give to screen. No half line.

```kavach
fn main() {
    const price = 40
    print("Hello")
    print(price * 3)
    print([1, 2, 3])
}
```

It prints, checked against a real run:

```
Hello
120
[1, 2, 3]
```

1. Line 3, `print("Hello")`: print starts a line in a buffer in RAM. "Hello" is text, so it is bytes already: its 5 bytes are copied in.
2. Line 3, `print("Hello")`: print adds the end of the line, one newline byte (\n). The line is whole: 6 bytes.
3. Line 3, `print("Hello")`: Now the line is written in one go: a system call hands its 6 bytes to the OS kernel, which passes them to the terminal, and the terminal draws them. The runtime decides when, while running: once the line is whole. The next line starts in an empty buffer.
4. Line 4, `print(price * 3)`: Before print can start, price * 3 is worked out in the core: 120, a whole number. A number is held in binary, not as text.
5. Line 4, `print(price * 3)`: The runtime, while running, turns 120 into the digits 1, 2 and 0: three bytes of text. Then the newline: the line is whole, 4 bytes.
6. Line 4, `print(price * 3)`: Written in one go, like the first: the terminal shows 120 on a line of its own.
7. Line 5, `print([1, 2, 3])`: The list is turned into text piece by piece: [, then 1, then a comma and a space, and so on to ], then the newline. 10 bytes: more than one 8-byte cell. Nothing is written while the line is half made.
8. Line 5, `print([1, 2, 3])`: The whole line goes to the kernel in one go. So another task's print can never land in the middle of it: each line comes out whole.

## Part 2: Functions

### [days_to_save(100, 30): one call, step by step](https://kavachlang.com/docs/functions/functions/returning-a-value/#scene-call)

Caveman says: Main call function. 100 and 30 go in register. Call push way-back on stack. Function count in register only. Answer 4 go in rax. Frame pop. Main take 4.

```kavach
fn days_to_save(goal: Int, per_day: Int) -> Int {
    let saved = 0
    for day in 1..=goal {
        saved += per_day
        if saved >= goal {
            return day
        }
    }
    0
}

fn main() {
    const days = days_to_save(100, 30)
    print(days)
}
```

It prints, checked against a real run:

```
4
```

1. Line 13, `const days = days_to_save(100, 30)`: main calls days_to_save(100, 30). The OS picked a core to run it (here core 0), while running. The compiler, while compiling, put 100 and 30 straight into the first two argument registers, as the platform's calling convention says. It also kept this a real call: a function that returns from inside a loop is not copied into its caller.
2. Line 13, `const days = days_to_save(100, 30)`: Before the call, a check the compiler put there runs: the core compares the stack pointer with the stack's limit. There is room, so the call goes on. Past the limit, the program would stop with a clear panic.
3. Line 1, `fn days_to_save(goal: Int, per_day: Int) -> Int {`: The call writes the return address, where main goes on, onto the stack in RAM, and jumps to days_to_save. A new frame starts below main's.
4. Line 1, `fn days_to_save(goal: Int, per_day: Int) -> Int {`: The function's first instructions, which the compiler wrote, save three of main's registers into the frame: main's frame pointer, and two registers this function will use. The convention says it must put them back, so main finds them as it left them.
5. Line 2, `let saved = 0`: saved starts at 0, in a register. goal, per_day, saved and day all stay in registers for the whole call: the frame holds none of them.
6. Line 4, `saved += per_day`: Round 1: day is 1, and saved becomes 30. After each add, the core checks the overflow flag: a sum too big for an Int would stop the program.
7. Line 5, `if saved >= goal {`: Is 30 at least 100? No, so the loop goes round again.
8. Line 4, `saved += per_day`: Rounds 2 and 3: saved becomes 60, then 90. Each round only changes registers inside the core; nothing touches memory.
9. Line 5, `if saved >= goal {`: Round 4: saved becomes 120, and 120 >= 100 is true.
10. Line 6, `return day`: return day puts 4 in rax, where a result goes back. The last instructions, which the compiler wrote, put main's three registers back from the frame.
11. Line 6, `return day`: ret reads the return address from the stack and jumps back into main. The frame is popped: the stack pointer moves back up, and those bytes are free at once. Code the compiler wrote does it: nothing is counted or searched.
12. Line 13, `const days = days_to_save(100, 30)`: main takes the result from rax: days is 4. It never goes to memory either: it goes straight on to print.
13. Line 14, `print(days)`: print asks the operating system's kernel to write 4 to the program's output. The stack holds only main's frame again.

### [factorial(10): the calls that really happen](https://kavachlang.com/docs/functions/recursion/#scene-factorial)

Caveman says: Compiler copy factorial into itself. One real call do four step. main do 10, call 9. factorial(9) do 9, 8, 7, 6, call 5. factorial(5) do 5, 4, 3, 2. 1? Stop, no call. Answers multiply back. Two box on stack, not ten.

```kavach
fn factorial(n: Int) -> Int {
    if n <= 1 {
        return 1
    }
    n * factorial(n - 1)
}

fn main() {
    const x = factorial(10)
    print(x)
}
```

It prints, checked against a real run:

```
3628800
```

1. Line 9, `const x = factorial(10)`: The compiler, while compiling, copied factorial into main once, so main does the first level itself: 10 is not <= 1. It also copied factorial's quick exit in front of the call: 9 <= 1? No. The OS picked a core to run it (here core 0), while running.
2. Line 9, `const x = factorial(10)`: A real call, factorial(9), with 9 in the argument register. First a check the compiler put there: is there room on the stack? The limit sits 8 MB above the stack's bottom, so this check fires long before the guard page below, which is only a backstop. Then the call writes the return address and jumps.
3. Line 1, `fn factorial(n: Int) -> Int {`: factorial(9) begins. Its first instructions save registers of main's it will use, into its own frame. Then it keeps n = 9 in rbx and n - 1 = 8 in rsi.
4. Line 2, `if n <= 1 {`: The compiler copied factorial into itself, so this one call checks four levels at once, all in registers: 9, 8, 7 and 6 are not <= 1. No call is made for 8, 7 or 6.
5. Line 5, `n * factorial(n - 1)`: The quick exit for the next level: 5 <= 1? No. So, after the same stack check, a second real call: factorial(5). 9 and 8 wait in rbx and rsi.
6. Line 1, `fn factorial(n: Int) -> Int {`: factorial(5) begins, with the same code. It needs rbx and rsi itself, so it first saves factorial(9)'s 9 and 8 into its own frame. That is where the waiting values really are.
7. Line 2, `if n <= 1 {`: 5, 4, 3 and 2 are not <= 1. Then the quick exit: 1 <= 1 is true. factorial(1) is just 1, and no call is made.
8. Line 5, `n * factorial(n - 1)`: On the way back, the multiplies run in registers: 2 × 1 = 2, 3 × 2 = 6, 4 × 6 = 24, 5 × 24 = 120. Every multiply is checked for overflow. 120 goes in rax.
9. Line 5, `n * factorial(n - 1)`: factorial(5) puts 9 and 8 back into rbx and rsi, reads its return address and jumps back. Its frame is popped by code the compiler wrote: no count, no search, those bytes are free again at once.
10. Line 5, `n * factorial(n - 1)`: Back in factorial(9): 6 × 120 = 720, 7 × 720 = 5040, 8 × 5040 = 40320, 9 × 40320 = 362880. It puts main's registers back and returns. Only main's frame is left.
11. Line 9, `const x = factorial(10)`: main does its own level: 10 × 362880 = 3628800, so x is 3628800. Two real calls did the work of ten.
12. Line 10, `print(x)`: print asks the operating system's kernel to write 3628800 to the program's output. Each real call's frame was freed the moment it returned.

## Part 3: Collections

### [A list in memory: index, push, grow, slice, swap](https://kavachlang.com/docs/collections/lists/#scene-list-buffer)

Caveman says: List is box with count. Items in other box, side by side. Read item: check, then one load. Push: room? Put there. No room? Bigger box. Slice: new list, copy. Swap: two item trade place, nothing copy.

```kavach
let xs = [3, 1, 4]
print(xs[1])
xs.push(5)
xs.push(9)
const firsts = xs[:2]
xs[0] = 7
xs.swap(0, 4)
print(firsts)
print(xs)
```

It prints, checked against a real run:

```
1
[3, 1]
[9, 1, 4, 5, 7]
```

1. Line 1, `let xs = [3, 1, 4]`: The runtime makes the list while running, in two pieces: a 48-byte list object (a 24-byte header with the count, then the buffer's address, the length and the capacity), and apart from it a buffer of exactly 3 slots. Whole numbers sit in the buffer itself, 8 bytes each: no object per item.
2. Line 2, `print(xs[1])`: Reading xs[1]: code the compiler wrote checks the index with one compare, 1 < len 3. A negative index counts as a huge unsigned number here, so the same compare catches it too. Then one load from ptr + 1 × 8 = 0x2008 gives 1.
3. Line 3, `xs.push(5)`: push checks two things inline: the count is 1, and len < cap. 3 < 3 is false, so the code calls the runtime. The runtime, while running, grows the buffer the way Rust's Vec does: room for 6, double. 5 goes in slot 3, len 4. A bigger buffer may move to a new address, with the items copied there: the allocator decides that, while running. It is drawn in place.
4. Line 4, `xs.push(9)`: Now there is room: count 1 and 4 < 6, so the code the compiler wrote stores 9 at ptr + 4 × 8 and sets len to 5. The runtime isn't called at all.
5. Line 5, `const firsts = xs[:2]`: A slice is a new value: the language says so, and the runtime copies at once, while running. It makes a new list object and a buffer of exactly 2 slots, and copies 3 and 1 into them. xs is not changed: still count 1.
6. Line 6, `xs[0] = 7`: Setting an item checks the same way inline: count 1, and 0 < len 5. 7 goes in place at 0x2000. firsts still holds 3: it is a copy, not a view of xs.
7. Line 7, `xs.swap(0, 4)`: swap is a call into the runtime, while running. It checks both indices against len 5, as xs[i] does: an index out of range would stop the program, with xs unchanged. The count is 1, so nothing else holds xs and nothing is copied. The two 8-byte words at 0x2000 and 0x2020 change places. Nothing is counted: text and records swap the same way, their words moving.
8. Line 8, `print(firsts)`: firsts' last use, marked by the compiler while compiling: print takes the list and lets it go. Its count falls to 0, so the runtime frees its object and buffer while running. They go grey where they were.
9. Line 9, `print(xs)`: xs's last use, also marked by the compiler: freed the same way. Nothing searched for garbage: each list was let go at its last use.

### [map, filter, sum: as written, and fused into one loop](https://kavachlang.com/docs/collections/lists/map-filter-sum/#scene-chain)

Caveman says: As written: map make list, filter make list, sum add. Fused: one loop, each item go all the way, no list in middle. Same answer.

```kavach
const prices = [120, 40, 300, 75]
const total = prices.map(p => p * 2).filter(p => p > 100).sum(p => p)
print(total)
```

It prints, checked against a real run:

```
990
```

1. Line 1, `const prices = [120, 40, 300, 75]`: Four prices: one list object and its buffer.
2. Line 2, `const total = prices.map(p => p * 2).filter(p => p > 100).sum(p => p)`: kavach run --native (Cranelift) runs the chain as written. The compiler, while compiling, wrote each lambda straight into a loop: no call per item, no closure object. First map's loop builds a new list: each price times 2, each multiply checked for overflow.
3. Line 2, `const total = prices.map(p => p * 2).filter(p => p > 100).sum(p => p)`: Then filter's loop reads that list and builds another: 240, 600 and 150 pass p > 100, and 80 doesn't. Nothing reads map's list after this, but filter's loop keeps it in a local of main. In native code, Cranelift or LLVM alike, main lets go of nothing its locals still hold: the operating system takes that memory back when the program ends. The compiler decided that while compiling.
4. Line 2, `const total = prices.map(p => p * 2).filter(p => p > 100).sum(p => p)`: Then sum's loop adds the items up in a register, each + checked for overflow. No list this time. Two lists were built on the way, each written item by item and read once.
5. Line 3, `print(total)`: 990 is printed.
6. Line 2, `const total = prices.map(p => p * 2).filter(p => p > 100).sum(p => p)`: The same line in a program built with kavach build (LLVM). While compiling, the compiler saw that each list in between is read only by the next loop, and fused the three loops into one. Each price goes through map, then filter, then into the total, in registers: 120 × 2 = 240, kept, total 240.
7. Line 2, `const total = prices.map(p => p * 2).filter(p => p > 100).sum(p => p)`: 40 × 2 = 80 fails p > 100 and is left out at once; 300 × 2 = 600 is added: total 840. No item is written to memory.
8. Line 2, `const total = prices.map(p => p * 2).filter(p => p > 100).sum(p => p)`: 75 × 2 = 150 is added: 990, the same answer, and no list was ever built. A fused loop does the work in a new order, so a failed check could stop at another place. So the compiler keeps the code as written beside it: if a check in the fused loop fails, that code runs instead, and the panic names the right line.
9. Line 3, `print(total)`: 990 again: both ways print the same.

### [Finding a key in a dict, before and after it has an index](https://kavachlang.com/docs/collections/dicts/reading-a-value/#scene-dict-lookup)

Caveman says: Dict keep things in order. Each key keep its hash. Few things? Check hashes one by one. Many things? Index say where. Few steps. Seed new each run.

```kavach
let ages = {"asha": 31, "ravi": 27, "omar": 45}
print(ages["ravi"] ?? 0)
print(ages["zoe"] ?? 0)
for name in ["bo", "cy", "di", "ed", "fay", "gus"] {
    ages[name] = 20
}
print(ages["omar"] ?? 0)
```

It prints, checked against a real run:

```
27
0
45
```

1. Line 1, `let ages = {"asha": 31, "ravi": 27, "omar": 45}`: The runtime makes the dict while running: one 64-byte object with the count, pointing to its table. The entries sit in the order they were added, key then value, and each key's hash is kept beside them. A key is a pointer to its text. With up to 8 entries, and keys that aren't whole numbers, there is no index.
2. Line 2, `print(ages["ravi"] ?? 0)`: To find "ravi", the core hashes its bytes, 8 at a time, mixed with this run's seed. The runtime picked the seed at random when the program started, so nobody can know ahead which keys collide.
3. Line 2, `print(ages["ravi"] ?? 0)`: No index, so the runtime compares the stored hashes in order: h(asha) differs, h(ravi) matches. It compares the key's text too, to be sure, then reads the value beside it: 27. With text keys and plain values, whole numbers here, a read with ?? is one runtime call that makes no optional value.
4. Line 3, `print(ages["zoe"] ?? 0)`: h(zoe) matches none of the three stored hashes, so "zoe" isn't there, and no key text needed comparing. The read gives none, and ?? gives 0.
5. Line 5, `ages[name] = 20`: Five rounds add bo to fay. Nobody else holds the dict: the runtime sees count 1 while running, so each new entry goes at the end, in place, with its hash. 8 entries: still no index. When a buffer is full the runtime grows it while running, and it may move; it is drawn in place.
6. Line 5, `ages[name] = 20`: The 9th entry, "gus": past 8, the runtime builds an index while running. 32 positions, a power of two at least twice the entries, so it stays at most half full. Each entry goes in at its hash's position, or the next free one. Here "fay" found position 12 taken, so it went on to 13. The hashes were kept, so no key is hashed again.
7. Line 7, `print(ages["omar"] ?? 0)`: Now a lookup goes through the index: h(omar) & 31 gives position 0. It holds 3: entry 3. Its kept hash matches and its key is "omar": 45. A few probes at most, however big the dict grows.

### [Which sort runs, and when sorting copies](https://kavachlang.com/docs/collections/sorting/#scene-sorting)

Caveman says: Whole numbers? Sort by digits, no compare. Few numbers? Compare. Text? Compare, keep equal ones in order. Nobody else hold list? Sort it where it is. Someone else hold it? Copy first.

```kavach
const ages = [42, -7, 0, 1_000, 3]
const sorted = ages.sort()
print(ages)
print(sorted)
print(["pear", "Fig", "apple"].sort())
let big: [Int] = []
for i in 0..1_000 {
    big.push(i * 7_919 % 1_000)
}
const order = big.sort()
print(`{order[0]} {order[1]} {order[999]}`)
```

It prints, checked against a real run:

```
[42, -7, 0, 1000, 3]
[-7, 0, 3, 42, 1000]
["Fig", "apple", "pear"]
0 1 999
```

1. Line 1, `const ages = [42, -7, 0, 1_000, 3]`: A list of 5 whole numbers: one list object, and a buffer with the numbers in it.
2. Line 2, `const sorted = ages.sort()`: ages is read again on the next line, so the compiler, while compiling, makes sort get a second hold: count 2. While running, the runtime sees count 2 and copies first: sorted gets its own list, and ages keeps its order. The compiler passed the item type, Int; the runtime picks the sort from it and the length. Under 512 items: a comparison sort, Rust's unstable one, a quicksort kind. Equal whole numbers can't be told apart, so their order doesn't matter.
3. Line 3, `print(ages)`: ages's last use, marked by the compiler while compiling: printed, then freed. It was never changed.
4. Line 4, `print(sorted)`: sorted's last use: printed, then freed.
5. Line 5, `print(["pear", "Fig", "apple"].sort())`: Text needs comparing, so the runtime, while running, picks a stable merge sort (Rust's standard sort), by Unicode code point: capital F comes before small a. This list is held by nobody else (count 1), so it isn't copied first. Its short texts sit inside its buffer, 16 bytes each; for the sort they are made into text objects and put back. Printed, then freed.
6. Line 8, `big.push(i * 7_919 % 1_000)`: 1,000 pushes fill big with 0 to 999 in a mixed order. The buffer grows as it fills, while running; it may move, and is drawn in place.
7. Line 10, `const order = big.sort()`: big's last use, marked by the compiler while compiling: sort takes it over (a move), so the count stays 1 and the runtime sorts it where it is, no copy. order is the same list. 1,000 whole numbers, 512 or more: a radix sort. The runtime makes a scratch buffer of 1,000 slots for it, while running.
8. Line 10, `const order = big.sort()`: One read counts every 8-bit digit of every number. The sign bit is flipped first, so negative numbers would come first; then the 54 high bits are the same in every number, and are skipped: 0 to 999 need only 10 bits, so 2 passes. Pass 1 places each number into the scratch buffer by its low 8 bits, keeping the order of numbers with the same digit. No two numbers are ever compared.
9. Line 10, `const order = big.sort()`: Pass 2 places them back into big's own buffer by bits 8 and 9: sorted. Two passes end where they began, so nothing is copied back; with an odd number of passes, the result would be in the scratch buffer and the runtime would copy it back. The runtime frees the scratch buffer.
10. Line 11, `print(`{order[0]} {order[1]} {order[999]}`)`: order[0] is 0, order[1] is 1, order[999] is 999: three loads, each after its index check.

## Part 6: Memory

### [A list changed while shared is copied then](https://kavachlang.com/docs/memory/values-not-references/#scene-memory-copy)

Caveman says: Two name. One list. Change list? Copy first. Now two list.

```kavach
const a = [2, 3, 4, 5]
let b = a
b.push(6)
print(`a={a}`)
print(`b={b}`)
```

It prints, checked against a real run:

```
a=[2, 3, 4, 5]
b=[2, 3, 4, 5, 6]
```

1. Line 1, `const a = [2, 3, 4, 5]`: One object, held by a.
2. Line 2, `let b = a`: b holds the same object: count 2, nothing copied yet.
3. Line 3, `b.push(6)`: b changes while a still holds the object. The runtime sees count 2 while running, so now, and only now, it copies: b gets its own object with 6 added, and a keeps the original.
4. Line 4, `print(`a={a}`)`: a's last use, marked by the compiler: count 1 → 0, and its object is freed.
5. Line 5, `print(`b={b}`)`: b's last use, marked by the compiler: its object is freed too.

### [Does b = a take new memory?](https://kavachlang.com/docs/memory/automatic-memory/memory-step-by-step/#scene-memory-share)

Caveman says: Two name. One list. No copy. Count go up. Compiler look ahead. Know last use. Let go there.

```kavach
const a = [2, 3, 4, 5]
const b = a
print(`a={a}`)
print(`b={b}`)
```

It prints, checked against a real run:

```
a=[2, 3, 4, 5]
b=[2, 3, 4, 5]
```

1. Line 1, `const a = [2, 3, 4, 5]`: One object: a header holding the count, then the four numbers side by side. The numbers are not objects of their own.
2. Line 2, `const b = a`: Nothing is allocated and nothing is copied. b holds the same object, and its count goes from 1 to 2.
3. Line 3, `print(`a={a}`)`: The compiler marked this as a's last use while compiling, so a lets go here: count 2 → 1.
4. Line 4, `print(`b={b}`)`: b's last use, marked by the compiler: count 1 → 0, and the object is freed at once.

### [A move: the last use hands the object over](https://kavachlang.com/docs/memory/automatic-memory/memory-step-by-step/#scene-memory-move)

Caveman says: Compiler look ahead. Old name not used again? Hand list over. No copy. Count stay same.

```kavach
const a = [2, 3, 4, 5]
const b = a
print(`b={b}`)
```

It prints, checked against a real run:

```
b=[2, 3, 4, 5]
```

1. Line 1, `const a = [2, 3, 4, 5]`: One object, held by a: count 1.
2. Line 2, `const b = a`: The compiler saw, while compiling, that a is never used again, so this is a move: b takes the object, the count stays 1, and a just ends. No count update runs.
3. Line 3, `print(`b={b}`)`: b's last use, marked by the compiler: count 1 → 0, and the object is freed.

### [Numbers are copied, 8 bytes at a time](https://kavachlang.com/docs/memory/automatic-memory/memory-step-by-step/#scene-memory-numbers)

Caveman says: Number small. Copy number. No need share. Change one? Other same.

```kavach
const a = 7
let b = a
b += 1
print(`a={a} b={b}`)
```

It prints, checked against a real run:

```
a=7 b=8
```

1. Line 1, `const a = 7`: A number is kept in place, in the variable itself: 8 bytes, often in a register. No object, no count.

## Part 7: Standard Library

### [A file's bytes: program, page cache, SSD](https://kavachlang.com/docs/standard-library/files/#scene-file-io)

Caveman says: Write: bytes go to OS. OS keep them in RAM, write to disk later. Read: OS give bytes back from RAM, fast. Lines: small bucket, fill, take one line, fill again.

```kavach
use std.fs

fn main() ! Error {
    try fs.write_text("notes.txt", `tea\ncake\n`)
    const all = try fs.read_text("notes.txt")
    print(all.len())
    for line in try fs.lines("notes.txt") {
        print(line)
    }
    for piece in try fs.chunks("notes.txt", 4) {
        print(piece.len())
    }
    try fs.remove("notes.txt")
}
```

It prints, checked against a real run:

```
9
tea
cake
4
4
1
```

1. Line 4, `try fs.write_text("notes.txt", `tea\ncake\n`)`: The runtime, while running, checks that notes.txt is inside the folders this task may use. Then it asks the OS, through system calls, to make a temporary file beside it and write the 9 bytes. During that call, the OS copies them from the program's memory into its page cache: memory in RAM that the OS keeps for files.
2. Line 4, `try fs.write_text("notes.txt", `tea\ncake\n`)`: Then the runtime renames the temporary file over notes.txt, so a crash leaves the old file or the new one, never half of one. There is no wait for the disk: the OS decides, while the program goes on, when to copy the pages to the SSD, usually seconds later. fs.write_durable waits for the disk instead. The text was the write's to let go: freed.
3. Line 5, `const all = try fs.read_text("notes.txt")`: read_text reads the whole file at once. Its pages are still in the page cache, so the OS copies them from there into the program's memory, most likely without touching the SSD; if they weren't, the OS would first read them from the SSD into the cache. The runtime makes one text value: up to 30 bytes fit inside its 64-byte object.
4. Line 6, `print(all.len())`: 9 characters: "tea", a line break, "cake", a line break.
5. Line 7, `for line in try fs.lines("notes.txt") {`: fs.lines opens the file and gives a reader with an 8 KB buffer, Rust's default size. The first line asked for makes one read call for up to 8 KB: the whole 9-byte file lands in the buffer. A big file comes in 8 KB at a time, never all at once.
6. Line 8, `print(line)`: The runtime cuts the buffer at the first line break and makes a new text value, "tea". print writes it.
7. Line 8, `print(line)`: "cake" comes from the same buffer: no system call this time. Each round's line is let go at its last use, the print: the compiler marked it while compiling, and print frees it. The next read finds the end of the file, and the loop stops.
8. Line 10, `for piece in try fs.chunks("notes.txt", 4) {`: fs.chunks opens a reader of its own, also with an 8 KB buffer. Each piece is a new Bytes value of at most 4 bytes. Pieces this small are read through that buffer, when the loop asks. Pieces of 1 MB or more skip the buffer: a helper thread the runtime starts reads them through a second handle to the file, one piece ahead, so the disk and the loop work at the same time.
9. Line 11, `print(piece.len())`: Three pieces: 4 bytes, 4 bytes, then the last 1.
10. Line 13, `try fs.remove("notes.txt")`: fs.remove asks the OS to remove notes.txt.

### [One frame through a drawing pipeline](https://kavachlang.com/docs/standard-library/gpu-screens/#scene-gpu-draw)

Caveman says: Two small fn. One say where corner go. One say what color pixel is. Compiler turn both into GPU program. Runtime ready it before any frame. Each draw: send corners and dots to GPU. GPU paint. Screen show at its beat.

```kavach
use std.window
use std.gpu

type Corner {
    x: Float32
    y: Float32
}

type Dot {
    x: Float32
    y: Float32
    heat: Float32
}

type Camera {
    zoom: Float32
}

type Lit {
    position: (Float32, Float32, Float32, Float32)
    heat: Float32
}

gpu vertex fn place(c: Corner, d: Dot, cam: Camera) -> Lit {
    Lit(position: ((c.x + d.x) * cam.zoom, (c.y + d.y) * cam.zoom, 0.0, 1.0), heat: d.heat)
}

gpu fragment fn glow(l: Lit) -> (Float32, Float32, Float32, Float32) {
    (l.heat, 0.2, 1.0 - l.heat, 1.0)
}

fn main() ! Error uses Window {
    const win = try window.open("Swarm", 640, 480)
    const screen = try gpu.screen(win)
    const dots = gpu.pipeline(place, glow)
    const square = [Corner(x: -0.1, y: -0.1), Corner(x: 0.1, y: -0.1), Corner(x: 0.1, y: 0.1), Corner(x: -0.1, y: 0.1)]
    const corners: [UInt32] = [0, 1, 2, 0, 2, 3]
    const swarm = [Dot(x: -0.5, y: 0.0, heat: 0.2), Dot(x: 0.5, y: 0.25, heat: 0.9)]
    for _ in 0..600 {
        const frame = try screen.frame()
        frame.clear(0.0, 0.0, 0.0)
        frame.draw(dots, square, instances: swarm, shared: Camera(zoom: 1.0), indices: corners)
        frame.show()
    }
}
```

It prints, checked against a real run:

```
gpu-draw.kav: no errors
```

1. Line 24, `gpu vertex fn place(c: Corner, d: Dot, cam: Camera) -> Lit {`: While compiling, the compiler checks place and glow, and that glow takes what place gives. It writes both into one WGSL module, a GPU program. Its first line tells the runtime how the buffers are laid out: a corner is 2 Float32s, a dot 3, the shared Camera 1.
2. Line 34, `const screen = try gpu.screen(win)`: The runtime, while running, readies the window for the program's own GPU, the one the settings name or else the best one: an sRGB color format when the screen offers one, else its first format, and Fifo, which shows each picture at the screen's next refresh (vsync), with at most 2 pictures waiting. A pipeline made before this would be compiled for its color format now.
3. Line 35, `const dots = gpu.pipeline(place, glow)`: A pipeline made while a screen is open is compiled at once, for each open screen's color format: ahead, never in the middle of a frame. The GPU's driver turns the WGSL into the GPU's own code and holds it, ready for every frame; where it keeps it is the driver's choice. Kavach keeps only a handle to it, and saves nothing between runs.
4. Line 40, `const frame = try screen.frame()`: The next picture to draw into, as big as the window is now. When 2 pictures already wait for the screen, this waits for its next refresh, so the loop runs at the screen's rate. clear then fills it with black.
5. Line 42, `frame.draw(dots, square, instances: swarm, shared: Camera(zoom: 1.0), indices: corners)`: Before anything is drawn, the runtime checks, while running, that each of the 6 indices names one of square's 4 corners. An index of 4 or more would stop the program here with a panic, and nothing would be drawn.
6. Line 42, `frame.draw(dots, square, instances: swarm, shared: Camera(zoom: 1.0), indices: corners)`: Each draw makes new buffers in VRAM and copies them over: the vertices, the instances, the indices and the shared value. Only a list a GPU map left in GPU memory is drawn where it is, with nothing copied. The draw is noted in the frame; the GPU hasn't drawn yet.
7. Line 43, `frame.show()`: show sends the frame's work, the clear and the draw, to the GPU in one go, and asks for the picture to be shown. The CPU goes on to the next round of the loop while the GPU draws.
8. Line 25, `Lit(position: ((c.x + d.x) * cam.zoom, (c.y + d.y) * cam.zoom, 0.0, 1.0), heat: d.heat)`: The GPU runs place on its many small cores, for each corner of each dot: 4 corners × 2 dots. Corner (-0.1, -0.1) of dot 0 lands at (-0.6, -0.1). heat goes on to glow. An overflow here gives a wrong value, not a panic: the GPU can't stop in the middle of a frame.
9. Line 29, `(l.heat, 0.2, 1.0 - l.heat, 1.0)`: The GPU joins the corners into triangles, finds the pixels inside each, and runs glow once for each of them: dot 0's pixels get (0.2, 0.2, 0.8), blue; dot 1's (0.9, 0.2, about 0.1), red. Each lands in the picture.
10. Line 43, `frame.show()`: At the screen's next refresh the picture is shown: Fifo, vsync. Then the loop draws the next frame, 600 in all, with new buffers each time.

## Part 8: Networks

### [One HTTPS request: from your code to a server and back](https://kavachlang.com/docs/networks/http/sessions/#scene-https-get)

Caveman says: Ask OS: where server? Shake hands. Make secret talk. Send few lines of text. Wait, not hold core. Answer come in pieces. Put together. Done? Say bye.

```kavach
use std.http

fn main() ! Error {
    const session = try http.open("https://example.com")
    const page = try session.get("/")
    print(page.status)
    session.close()
}
```

It prints, checked against a real run:

```
https-get.kav: no errors
```

1. Line 4, `const session = try http.open("https://example.com")`: std.http, which is Kavach code, splits the URL: host example.com, port 443 added for https, and the path /. A session connects at once, not at its first request.
2. Line 4, `const session = try http.open("https://example.com")`: The runtime, while running, starts one OS thread just for this connect, and parks the task: other tasks keep running. The thread asks the OS to turn example.com into an address, through the system's resolver.
3. Line 4, `const session = try http.open("https://example.com")`: The thread connects to the first address the resolver gives, and today only that one, on port 443. The OS's TCP does the three-way handshake through the network card. The thread waits for it, up to 30 seconds.
4. Line 4, `const session = try http.open("https://example.com")`: Then TLS, by rustls inside the program, not the OS: the thread offers HTTP/1.1, the server sends its certificate, and rustls checks it against Mozilla's list of roots built into the program, plus any roots the program's own settings add, never the OS's store. Both sides agree on keys, so from now on every byte is encrypted.
5. Line 4, `const session = try http.open("https://example.com")`: The socket is ready. The runtime makes it non-blocking and adds it to the OS's readiness queue, the thread ends, and the task is woken with its session: one TLS connection, kept for the requests that follow.
6. Line 5, `const page = try session.get("/")`: session.get builds the request as text in memory: the request line, the host, and content-length: 0. Nothing else is added: no user-agent, no compression asked for.
7. Line 5, `const page = try session.get("/")`: It goes out in one write: rustls encrypts it, the OS's network stack sends it through the network card, and the internet carries it to the server.
8. Line 5, `const page = try session.get("/")`: Now the task waits for the reply and gives up its turn. When no task is ready, the scheduler's thread sleeps in the OS's readiness queue. There is no network thread: the OS wakes the thread when bytes arrive.
9. Line 5, `const page = try session.get("/")`: The server's answer reaches the network card, the OS keeps it in the socket's buffer and wakes the thread. Each read takes up to 64 KB, and rustls decrypts it. std.http adds each piece until the head is whole.
10. Line 5, `const page = try session.get("/")`: The head says the status, 200, and how many bytes the body has (content-length). Reading goes on until they are all there; then the task gets a Response: status, headers, and the body as Bytes.
11. Line 6, `print(page.status)`: page.status is a plain Int, and print writes it: 200 for this page.
12. Line 7, `session.close()`: close tells the server the encrypted talk is over (TLS close_notify), then the OS closes the connection. A session never closed is closed when its last holder lets go, without that goodbye.

## Part 9: Concurrency

### [spawn: a task on the same thread](https://kavachlang.com/docs/concurrency/tasks/#scene-spawn)

Caveman says: Spawn make small task. Same thread, own stack. Task wait in line. Main wait? Task run. Task done? Main go on.

```kavach
fn slow_double(n: Int) -> Int {
    n * 2
}

fn main() ! Error {
    const t = spawn slow_double(21)
    print("working meanwhile")
    print(try t.wait())
}
```

It prints, checked against a real run:

```
working meanwhile
42
```

1. Line 6, `const t = spawn slow_double(21)`: main works out the argument, 21, then spawns. main's thread hosts coroutines, so the runtime, while running, makes the task a coroutine on that same thread: no new OS thread. It gets a stack of its own (512 MB of address space; the OS gives it memory only as it is used) and a Task object on the heap. The scheduler puts it at the back of the ready queue, and main keeps the turn.
2. Line 7, `print("working meanwhile")`: main still has the turn, so it goes on. Its line goes out through the OS. The task waits in the ready queue: nothing runs it until main waits.
3. Line 8, `print(try t.wait())`: t.wait(): the task hasn't ended, so main waits and gives up the turn. The scheduler, while running, picks the first ready task. Passing the turn switches stacks on the same thread, with no system call: the OS sees nothing.
4. Line 2, `n * 2`: slow_double runs on the same core and the same thread, with its own stack: 21 * 2 = 42.
5. Line 3, `}`: It returns: 42 goes into the Task object on the heap, and the task ends. The runtime drops its coroutine, and the task's stack with it, at once. main's wait is over, so the scheduler, while running, makes main ready.
6. Line 8, `print(try t.wait())`: main runs again: wait() reads 42 from the Task object, and print writes it out. One thread did all of it, on one core, taking turns.

### [A ticker, its timers, and its end](https://kavachlang.com/docs/concurrency/tasks-never-leak/#scene-ticker)

Caveman says: Ticker wait one beat, then tick. Tick 0, tick 1. Sleep not hold core. Function end? Ticker stop. Nothing left running.

```kavach
use std.time

fn watch() {
    const _ticker = spawn {
        for tick in time.every_ms(400) {
            print(`tick {tick}`)
        }
    }
    time.sleep_ms(1000)
}

fn main() {
    watch()
    print("watching stopped")
}
```

It prints, checked against a real run:

```
tick 0
tick 1
watching stopped
```

1. Line 13, `watch()`: main calls watch(): a plain call, in the same task. watch spawns, so the compiler, while compiling, wrapped it: when it returns, it cancels the tasks it spawned that still run, then waits for them.
2. Line 4, `const _ticker = spawn {`: The runtime, while running, makes the ticker a coroutine on main's thread, with its own stack. It is ready; watch keeps the turn.
3. Line 9, `time.sleep_ms(1000)`: watch sleeps 1000 ms: the scheduler notes a timer and parks it, so the ticker runs.
4. Line 5, `for tick in time.every_ms(400) {`: every_ms(400) doesn't tick at once: the compiler, while compiling, made each round a sleep until its start, and the first start is one interval from now. So the ticker parks with a timer at 400 ms.
5. Line 5, `for tick in time.every_ms(400) {`: Nothing is ready. The scheduler, while running, takes the earliest timer, 400 ms, and the thread waits on a condition variable until then. The OS takes it off the core: no core is held while tasks sleep.
6. Line 6, `print(`tick {tick}`)`: At 400 ms the OS wakes the thread, and the scheduler runs the ticker: its first round. Ticks count from 0. The next round starts 400 ms after this one did, at 800 ms. A late round doesn't catch up: the next one still waits 400 ms from when this one really started.
7. Line 6, `print(`tick {tick}`)`: At 800 ms, tick 1. Its next round would start at 1200 ms, so it parks with that timer.
8. Line 9, `time.sleep_ms(1000)`: At 1000 ms watch's timer comes first: the scheduler runs watch, and its sleep ends. The ticker still waits for 1200 ms.
9. Line 10, `}`: watch returns, and the join the compiler put at the end of the function runs: first it cancels the ticker, then it waits for it to end. The runtime ends the ticker's wait at once, long before 1200 ms. Each function on the ticker's stack returns at once, letting go of what it holds. Its timer is left behind; the scheduler skips it.
10. Line 14, `print("watching stopped")`: The ticker has ended, and its stack is freed. watch is back in main, which prints. Nothing is left running in the background.

### [A channel between two tasks: full makes the sender wait, empty the receiver](https://kavachlang.com/docs/concurrency/channels/#scene-channel)

Caveman says: Channel is small line of box. Line full? Putter wait. Line empty? Taker wait. Waiting task not hold core. Close? Taker stop when line empty.

```kavach
fn main() {
    const (send, receive) = Channel<Int>(capacity: 2)
    const _producer = spawn {
        for i in 1..5 {
            send.put(i * 10)
        }
        send.close()
    }
    for n in receive {
        print(n)
    }
}
```

It prints, checked against a real run:

```
10
20
30
40
```

1. Line 2, `const (send, receive) = Channel<Int>(capacity: 2)`: Channel<Int>(capacity: 2) makes one channel object on the heap; send and receive both point to it. It holds a queue with room for 2 values, two lists of tasks waiting (to take, and to put), and a lock the runtime holds only while a value or a waiter goes in or out.
2. Line 3, `const _producer = spawn {`: The producer becomes a coroutine on main's thread (the runtime, while running), ready. main keeps the turn.
3. Line 9, `for n in receive {`: main takes: the queue is empty and open, so the runtime, while running, notes main as a taker and parks it. The scheduler gives the turn to the producer.
4. Line 5, `send.put(i * 10)`: put(10): there is room, so 10 goes in, and the runtime makes the first waiting taker, main, ready. Ready doesn't mean running: the producer keeps the turn until it waits.
5. Line 5, `send.put(i * 10)`: put(20): room for one more. Now the queue holds 2 values: it is full.
6. Line 5, `send.put(i * 10)`: put(30): full. The runtime, while running, notes the producer as a putter and parks it, so a fast producer can't fill memory. The scheduler runs main, ready since put(10).
7. Line 10, `print(n)`: main takes 10, the oldest value. That makes room, so the runtime makes the waiting producer ready. main keeps the turn and prints 10.
8. Line 10, `print(n)`: main takes 20 and prints it. The queue is empty again.
9. Line 9, `for n in receive {`: main takes again: empty, so the runtime parks it. The producer runs: its put(30) tries again.
10. Line 5, `send.put(i * 10)`: 30 goes in, and the runtime makes main ready.
11. Line 5, `send.put(i * 10)`: 40 goes in: full again, but the loop is over.
12. Line 7, `send.close()`: close() marks the channel closed and wakes every task waiting on it; none is. The values in it stay to be taken. Then the producer ends, and its stack is freed.
13. Line 10, `print(n)`: main runs: it takes 30 and prints it.
14. Line 10, `print(n)`: Then 40.
15. Line 9, `for n in receive {`: main takes once more: empty and closed, so the loop ends, without waiting. The values came out in the order they went in.

### [Two tasks sleep: who wakes them, and when](https://kavachlang.com/docs/concurrency/taking-turns/#scene-turns)

Caveman says: Task sleep? Not hold core. Scheduler write down wake time. Nothing to do? Thread sleep in OS. Time come? OS wake thread. Short sleep wake first.

```kavach
use std.time

fn report(name: String, ms: Int) -> String {
    time.sleep_ms(ms)
    print(`{name} done`)
    name
}

fn main() ! Error {
    const slow = spawn report("slow", 400)
    const fast = spawn report("fast", 100)
    print("both started")
    print(`{try slow.wait()} and {try fast.wait()} are back`)
}
```

It prints, checked against a real run:

```
both started
fast done
slow done
slow and fast are back
```

1. Line 10, `const slow = spawn report("slow", 400)`: main spawns slow. The runtime, while running, makes it a coroutine on main's thread, with its own stack, and puts it in the ready queue. The task that spawned it keeps running.
2. Line 11, `const fast = spawn report("fast", 100)`: fast too, behind slow in the ready queue. Both are ready, but main still has the turn.
3. Line 12, `print("both started")`: So main prints first.
4. Line 13, `print(`{try slow.wait()} and {try fast.wait()} are back`)`: main waits for slow and gives up its turn. The scheduler, while running, runs the task that became ready first: slow. The switch is a change of stacks on the same thread, with no system call.
5. Line 4, `time.sleep_ms(ms)`: slow asks to sleep 400 ms. The scheduler notes a timer, counted from when slow became ready, and parks slow: no thread sleeps for it, and no core is held. fast runs.
6. Line 4, `time.sleep_ms(ms)`: fast parks too, with a timer at 100 ms. Now nothing is ready. The scheduler, while running, takes the earliest timer, 100 ms, and the thread waits on a condition variable until then: the OS takes it off the core, which is free for other programs. (A task waiting on a socket would make it wait on the OS's readiness queue instead: epoll, kqueue or IOCP.)
7. Line 5, `print(`{name} done`)`: At 100 ms the OS wakes the thread. The scheduler finds fast's time has come and makes it ready, and it is the only one: fast prints.
8. Line 6, `name`: fast returns its name and ends; its stack is freed. Nothing is ready, so the thread waits again, now until 400 ms.
9. Line 5, `print(`{name} done`)`: At 400 ms slow wakes and prints. The sleeps overlapped: slow's 400 ms began at the same moment as fast's 100.
10. Line 13, `print(`{try slow.wait()} and {try fast.wait()} are back`)`: slow ended, which main waited for, so main runs. fast ended long ago, so fast.wait() doesn't wait. About 400 ms in all, not 500, and the same order on every run: the scheduler decides it from the program, not from the machine.

### [spawn, spawn cores, spawn thread: which thread runs each task](https://kavachlang.com/docs/concurrency/how-tasks-run/#scene-spawn-kinds)

Caveman says: Plain spawn: same thread, take turn. Spawn cores: next worker, maybe other core. Spawn thread: new thread, always. Same answer every way.

```kavach
fn sum_to(n: Int) -> Int {
    let total = 0
    for i in 0..n {
        total += i
    }
    total
}

fn main() ! Error {
    const a = spawn sum_to(10)
    const b = spawn cores sum_to(20)
    const c = spawn cores sum_to(30)
    const d = spawn thread sum_to(40)
    print(`{try a.wait()} {try b.wait()} {try c.wait()} {try d.wait()}`)
}
```

It prints, checked against a real run:

```
45 190 435 780
```

1. Line 9, `fn main() ! Error {`: The file has a spawn cores, so the compiler, while compiling, put a call at the very top that starts the workers, one per core. The runtime, while running, starts threads for workers 1 to 3; worker 0 is main's own thread. A worker with nothing to do sleeps, on no core.
2. Line 10, `const a = spawn sum_to(10)`: A plain spawn on main's thread is a coroutine there (the runtime, while running): its own stack, the same thread, and a place in worker 0's ready queue. main keeps the turn.
3. Line 11, `const b = spawn cores sum_to(20)`: spawn cores sends its task to the next worker in turn, counting from worker 0. So this first one lands on worker 0, main's own: it becomes a coroutine here, just like a, with nothing copied.
4. Line 12, `const c = spawn cores sum_to(30)`: The next one goes to worker 1. It gets a copy of its values, here one number, so no object is shared between threads, and waits in worker 1's inbox. Worker 1's thread wakes and runs it as a coroutine there, while main goes on: each worker has its own turns. The OS picks the core.
5. Line 13, `const d = spawn thread sum_to(40)`: spawn thread always makes a new OS thread, with a 512 MB stack. Built by LLVM, it runs ahead: on a copy of its values, it computes at once, and waits for its turn only before something others could see, such as ending. A plain spawn inside d would make a thread too: d's thread hosts no coroutines.
6. Line 14, `print(`{try a.wait()} {try b.wait()} {try c.wait()} {try d.wait()}`)`: main waits for a. On worker 0 the scheduler, while running, gives the turn to the first ready task, a: a switch of stacks on the same thread.
7. Line 4, `total += i`: a adds up to 45 and ends, so main is ready, behind b and d. b, next in worker 0's ready queue, runs its loop.
8. Line 6, `total`: b ends with 190. Now d's turn comes: it has worked out 780 on its own thread, or finishes first, and only now does it end, in turn. Its thread ends with it.
9. Line 14, `print(`{try a.wait()} {try b.wait()} {try c.wait()} {try d.wait()}`)`: main runs and reads each result. c ran on worker 1 alongside all this: it has ended, or main waits for it here. Three ways to run, one output, the same on every run.

### [From a .kav file to a running program, three ways](https://kavachlang.com/docs/tools/the-kavach-command/#scene-compiler)

Caveman says: Read file. Cut in words. Make tree. Find names. Check types. Then three road. run: walk tree. run --native: make machine code in memory, go. build: make machine code, glue runtime, write file. GPU part get own code too.

```kavach
gpu fn double(x: Float32) -> Float32 {
    x * 2.0
}

fn main() {
    const xs: [Float32] = [1.0, 2.0, 3.0]
    print(xs.map(x => double(x)))
}
```

It prints, checked against a real run:

```
[2.0, 4.0, 6.0]
```

1. Line 1, `gpu fn double(x: Float32) -> Float32 {`: You type kavach run compiler.kav. kavach is a program running on the CPU: it asks the OS kernel to read the file, and the file's bytes come from the SSD into RAM. The first five stages are the same for every command.
2. Line 7, `print(xs.map(x => double(x)))`: The lexer cuts the text into tokens, the words of the language: print, (, xs, ., map, (, x, =>, double, and so on.
3. Line 7, `print(xs.map(x => double(x)))`: The parser arranges the tokens into a syntax tree: a call of print, holding a call of map on xs, holding a lambda that calls double.
4. Line 7, `print(xs.map(x => double(x)))`: The resolver links each name to what it means: double to the gpu fn on line 1, xs to the const on line 6, print to the built-in print.
5. Line 6, `const xs: [Float32] = [1.0, 2.0, 3.0]`: The checker works out every type and checks every rule: xs is a [Float32], and double takes and gives a Float32, so the call fits. kavach check stops here and says: no errors. A mistake stops every command here, before anything runs.
6. Line 7, `print(xs.map(x => double(x)))`: kavach run makes no machine code. The interpreter, part of kavach, walks the checked tree and does what each part says. It runs every map on the CPU, one item after another, and prints the list. It doesn't touch the GPU at all, unless KAVACH_GPU names a device, by number or by maker (or can't be read): then it looks for that device, to check it is there.
7. Line 2, `x * 2.0`: kavach run --native goes on from the checked tree to KIR, a simpler form of the program made for code generators. Its passes, while compiling, mark each name's last use and copy small functions into their callers.
8. Line 1, `gpu fn double(x: Float32) -> Float32 {`: The map might be worth running on the GPU, so the compiler, while compiling, also writes its kernel in WGSL, the GPU's own language, and keeps that text in the program. The GPU is not touched yet.
9. Line 7, `print(xs.map(x => double(x)))`: Cranelift turns the KIR into machine code for this CPU, straight into RAM. Nothing is written to the SSD.
10. Line 7, `print(xs.map(x => double(x)))`: The CPU runs that code at once. At its start, the runtime begins opening the GPU on a background thread, where the GPU's driver compiles the WGSL. A map of 3 items is far less work than using the GPU costs, so the runtime's cost check, while running, keeps it on the CPU. Once the GPU is open, a map goes there when it would take the CPU at least 2 ms; while the GPU is still opening, only one that would take 300 ms. KAVACH_GPU=on or check skips the cost check. The same list is printed.
11. Line 7, `print(xs.map(x => double(x)))`: kavach build makes the same KIR, then decides, while building: LLVM when it supports the program and its tools are found, else Cranelift. LLVM gets the KIR as LLVM IR text; opt -O3 makes it faster, and llc -O3 turns it into an object file of machine code.
12. Line 5, `fn main() {`: The platform's linker (link.exe on Windows, cc elsewhere) joins the object file with Kavach's runtime library into one executable, and the OS writes it to the SSD. Nothing has run yet: you run that file later, as often as you like, without kavach.

## Part 12: Speed

### [on cores: small ranges, taken in turn by every core](https://kavachlang.com/docs/speed/loops-on-all-cores/#scene-cores-loop)

Caveman says: Many rounds. Cut in small piles. Each core take next pile, again and again. Each round write own box. Answer same as one core.

```kavach
fn main() {
    let xs: [Float] = []
    let ys: [Float] = []
    for i in 0..1_000_000 {
        xs.push(Float(i % 1000) * 0.125)
        ys.push(0.0)
    }
    on cores for i in 0..1_000_000 {
        ys[i] = xs[i] * 2.5 + 1.0
    }
    print(ys[999_999])
}
```

It prints, checked against a real run:

```
313.1875
```

1. Line 4, `for i in 0..1_000_000 {`: A plain for fills xs and ys: one core, in order, round after round.
2. Line 8, `on cores for i in 0..1_000_000 {`: The compiler, while compiling, proved each round writes only its own ys[i], and moved the body into a function that runs a range of rounds. The runtime, while running, checks: 1,000,000 rounds (65,536 at least), few values from outside the loop (6 at most), 4 cores. So it spreads the loop: a range is the largest of 1,000,000 / (4 × 4), 4,096 and 1,000,000 / 256 + 1, so 62,500 rounds, 16 ranges. It wakes the threads it keeps for loops, and 3 of them join this one.
3. Line 9, `ys[i] = xs[i] * 2.5 + 1.0`: Each thread takes the next free range from a shared counter, one atomic add, and runs it. The OS puts the threads on cores. Each round writes only its own slot, so no two threads touch the same item.
4. Line 9, `ys[i] = xs[i] * 2.5 + 1.0`: A thread that finishes takes the next free range at once, so none waits for a slow one. Which thread takes which range changes from run to run: this is one run.
5. Line 9, `ys[i] = xs[i] * 2.5 + 1.0`: The last four ranges. When the counter passes 1,000,000, a thread finds no range left and stops.
6. Line 10, `}`: The loop's thread waits until the others have left, then checks: did any range fail a check, such as an overflow? None did, so the loop is over. Had one failed, the runtime would throw the work away and run the plain loop on one core, so the panic comes at the same round and line.
7. Line 11, `print(ys[999_999])`: Every round wrote its own slot, so ys is exactly what the plain loop makes, in round order.

### [A map on the GPU: copied over, run at once, left there](https://kavachlang.com/docs/speed/gpu/#scene-gpu-map)

Caveman says: Big list, heavy work? Runtime send to GPU. List go over. Many small cores work at once. Answer stay on GPU. CPU no wait. CPU read answer? Then answer come back. Once.

```kavach
gpu fn glow(x: Float32, gain: Float32) -> Float32 {
    let v = x
    for _ in 0..1000 {
        v = v * 0.99 + gain
    }
    v
}

fn main() {
    let pixels: [Float32] = []
    for i in 0..1_000_000 {
        pixels.push(Float32(i % 256) / 255.0)
    }
    const gain: Float32 = 0.25
    const lit = pixels.map(p => glow(p, gain))
    print(pixels.len())
    print(lit.all(v => 24.9 < v < 25.1))
}
```

It prints, checked against a real run:

```
1000000
true
```

1. Line 1, `gpu fn glow(x: Float32, gain: Float32) -> Float32 {`: While compiling, the compiler checks that glow uses only what a GPU can do, and writes it, with the lambda that calls it, as a WGSL kernel: a small GPU program kept inside this one. It also counts glow's work per item: 1000 rounds of a multiply and an add. As the program starts, the runtime opens the GPU and compiles that kernel for it, on a background thread, unless the GPU is set off.
2. Line 12, `pixels.push(Float32(i % 256) / 255.0)`: The CPU fills pixels in RAM: a million Float32s, 4 bytes each, side by side: 4 MB. A list of Float32 is packed, so its items are already in the form a GPU reads.
3. Line 15, `const lit = pixels.map(p => glow(p, gain))`: CPU or GPU? The runtime decides while running. The compiler counted about 7,000 steps per item; a million items make about 700 ms of CPU time. That is over the 2 ms that makes the GPU worth it, and over the 300 ms worth waiting for a GPU still opening, so if the GPU isn't open yet, the map waits for it. Less work stays on the CPU, as does every map on a machine with no usable GPU: the same output, more slowly. KAVACH_GPU, or [run] gpu in kavach.toml, changes this: on and check skip the check, cpu or off keep every map on the CPU, and a maker's name or a GPU number picks the GPU.
4. Line 15, `const lit = pixels.map(p => glow(p, gain))`: The runtime copies pixels over the PCIe link into the GPU's own memory, VRAM, as it is. Only lists already packed at 4 bytes (Int32, UInt32, Float32) go as they are: a [Bool] is widened to 4-byte words, and a record's fields narrowed from 8 to 4 bytes, on the CPU first. Every field of every item goes up. So do the captured values: gain, after the item count.
5. Line 4, `v = v * 0.99 + gain`: The GPU runs the kernel: one thread per item, in 3,907 groups of 256, on its many small cores at once. Each thread runs glow's 1000 rounds on its own pixel and writes the result into lit's buffer in VRAM. An item that overflowed a whole number, or divided by zero, would set the stop flag: what happened, its two numbers and the line.
6. Line 16, `print(pixels.len())`: The map didn't wait. lit is kept in a local, so the compiler, while compiling, marked this map to leave its result on the GPU (decision 0061): the runtime queued the work and went on. lit's list in RAM is made, filled with zeros until its items come back. The CPU prints 1000000 while the GPU may still be working. (With KAVACH_GPU=check, a result like a [Bool] that isn't packed at 4 bytes, or a list too big for one pass, the map waits and copies back instead.)
7. Line 17, `print(lit.all(v => 24.9 < v < 25.1))`: The first CPU read of lit. The compiler put a fetch before it, while compiling. The runtime waits for the GPU and reads the stop flag: 20 bytes back over PCIe. Had an item failed, its panic would show here, with glow's line, after line 16 had run. Another GPU wait, or the program's end, reads the flag too.
8. Line 17, `print(lit.all(v => 24.9 < v < 25.1))`: The flag is clear, so the runtime copies lit's 4 MB back over PCIe into its list in RAM, once. A map whose result is read at once, not kept in a local, waits for the GPU and copies it back by itself.
9. Line 17, `print(lit.all(v => 24.9 < v < 25.1))`: all runs on the CPU over lit's items: each is near 25, so it prints true. pixels and lit stay in GPU memory too: pixels went up in one piece, so it is kept. The runtime keeps up to 4 lists a map read or made, 512 MB at most, so a later map of either copies nothing over.

### [A list changed while shared is copied then](https://kavachlang.com/docs/concepts/values-not-shared-references/#scene-memory-copy)

Caveman says: Two name. One list. Change list? Copy first. Now two list.

```kavach
const a = [2, 3, 4, 5]
let b = a
b.push(6)

print(`b={b}`)
```

It prints, checked against a real run:

```
a=[2, 3, 4, 5]
b=[2, 3, 4, 5, 6]
```

1. Line 1, `const a = [2, 3, 4, 5]`: One object, held by a.
2. Line 2, `let b = a`: b holds the same object: count 2, nothing copied yet.
3. Line 3, `b.push(6)`: b changes while a still holds the object. The runtime sees count 2 while running, so now, and only now, it copies: b gets its own object with 6 added, and a keeps the original.

### [Does b = a take new memory?](https://kavachlang.com/docs/concepts/memory-without-a-garbage-collector/#scene-memory-share)

Caveman says: Two name. One list. No copy. Count go up. Compiler look ahead. Know last use. Let go there.

```kavach
const a = [2, 3, 4, 5]
const b = a
print(`a={a}`)
print(`b={b}`)
```

It prints, checked against a real run:

```
a=[2, 3, 4, 5]
b=[2, 3, 4, 5]
```

1. Line 1, `const a = [2, 3, 4, 5]`: One object: a header holding the count, then the four numbers side by side. The numbers are not objects of their own.
2. Line 2, `const b = a`: Nothing is allocated and nothing is copied. b holds the same object, and its count goes from 1 to 2.
3. Line 3, `print(`a={a}`)`: The compiler marked this as a's last use while compiling, so a lets go here: count 2 → 1.
4. Line 4, `print(`b={b}`)`: b's last use, marked by the compiler: count 1 → 0, and the object is freed at once.
